## Overview

회원 Repository를 memory에서 순수 JDBC, JdbcTemplate, JPA, Spring Data JPA로 단계적으로 교체하면 각 기술이 제거하는 반복 작업과 남겨 두는 제어 범위가 드러난다. Interface와 DI 덕분에 Service code는 유지한 채 data access 구현만 바꿀 수 있다. DB를 사용하는 test에서는 실제 Spring configuration과 transaction rollback을 이용해 통합 동작과 test 독립성을 함께 확인한다.

## H2 환경과 버전 주의

강의 자료는 Spring Boot 2.x 환경에는 H2 1.4.200, Spring Boot 3.x에는 H2 2.1.214 이상을 안내한다. 현재 환경에서는 사용하는 Spring Boot version과 호환되는 H2를 선택해야 한다.

> **Status: Outdated** (2021-12-01)
> 영상에서 H2 `1.4.200`을 고정해 설치하는 절차는 당시 Spring Boot 2.x 강의 환경을 위한 지침이다. 새로운 환경에 그대로 적용하지 말고 사용하는 Spring Boot version과 최신 강의 manual의 호환 안내를 우선한다. 다른 H2 version으로 DB file을 이미 열었다면 file format 충돌 가능성도 함께 확인한다.

최초 file DB 접속 예는 `jdbc:h2:~/test`, 이후 server mode 접속 예는 `jdbc:h2:tcp://localhost/~/test`다. 회원 table은 identity 방식 `id`, `name`, primary key로 구성한다.

### 최초 DB 생성과 이후 접속

H2는 가볍고 Web Console을 제공해 교육용 실습에 사용한다. 강의의 접속 순서는 다음과 같다.

1. H2 server를 실행한다. macOS/Linux는 `./h2.sh`, Windows는 `h2.bat`를 사용한다.
2. 최초 한 번은 `jdbc:h2:~/test`로 접속해 home directory에 `test.mv.db` file을 생성한다.
3. 이후에는 `jdbc:h2:tcp://localhost/~/test`로 접속한다. File을 직접 여는 대신 TCP socket을 사용하면 application과 Web Console이 같은 DB에 접근할 수 있다.
4. Application에서 DB를 사용하는 동안 H2 server가 실행 중이어야 한다. Server를 종료하면 connection refused 계열 오류가 발생한다.

Web Console URL에 IP가 표시돼 접속되지 않을 때는 host 부분만 `localhost`로 바꾸고 session key를 포함한 나머지 URL은 유지한다.

실습용 DB가 꼬였을 때는 Web Console 연결과 H2 server를 모두 종료한 뒤 `test.mv.db`를 지우고 최초 생성 단계부터 다시 시작할 수 있다. 이 조치는 저장 데이터를 삭제하므로 폐기 가능한 실습 DB에만 적용한다.

### 회원 schema와 identity

회원 table의 `id`는 Java의 `long`에 대응하는 `bigint`이고 primary key다. `generated by default as identity`를 사용하면 INSERT에서 id를 생략했을 때 DB가 값을 생성하고 증가시킨다. `name`은 `varchar(255)`로 저장한다.

```sql
create table member
(
    id   bigint generated by default as identity,
    name varchar(255),
    primary key (id)
);
```

Schema를 Web Console에만 남겨 두지 않고 project의 `sql/ddl.sql` 같은 file로 관리하면 Git에서 변경 이력을 추적할 수 있다.

## 순수 JDBC

`spring-boot-starter-jdbc`와 H2 driver를 추가하고 datasource URL, driver, username을 설정한다. 순수 JDBC Repository는 `Connection`, `PreparedStatement`, `ResultSet`을 직접 다루며 SQL 실행, exception 처리와 resource 반환까지 구현해야 한다.

이 단계는 반복 코드가 많지만 JDBC의 실제 작업 경계를 확인할 수 있다. `SpringConfig`에서 `MemberRepository` Bean만 memory 구현에서 JDBC 구현으로 교체하면 Service나 Controller는 그대로 유지된다.

### Spring Boot의 DataSource 구성

`build.gradle`에 JDBC starter와 H2 database client를 추가하고 `application.properties`에 접속 URL과 H2 driver를 설정하면 Spring Boot가 접속 정보를 이용해 `DataSource` Bean을 만든다. `JdbcMemberRepository`는 생성자로 `javax.sql.DataSource`를 주입받아 database connection을 얻는다.

### 저장 처리와 generated key

회원 저장은 다음 단계로 진행된다.

1. `insert into member(name) values(?)`처럼 parameter 자리를 `?`로 둔 SQL을 준비한다.
2. `PreparedStatement.setString(1, member.getName())`으로 첫 번째 parameter를 binding한다.
3. `executeUpdate()`로 INSERT를 실행한다.
4. Statement를 만들 때 generated key 반환 option을 지정하고 `getGeneratedKeys()`로 DB가 생성한 id를 받는다.
5. `ResultSet`에서 id를 꺼내 저장된 `Member` 객체에 설정한다.

조회는 `executeQuery()`가 반환한 `ResultSet`을 읽어 `Member`로 변환한다. 단건 조회는 결과가 없으면 `Optional.empty()`를 반환하고, 전체 조회는 row를 순회하며 `List<Member>`에 추가한다. 즉 순수 JDBC에서는 SQL 실행뿐 아니라 parameter binding, row-to-object mapping, 결과 없음 처리까지 개발자가 직접 작성한다.

### Connection과 resource 관리

DB connection은 외부 resource이므로 사용 후 반드시 반환해야 한다. 강의의 고전적인 구현은 `ResultSet`, `PreparedStatement`, `Connection`을 획득의 역순으로 닫고, 각 close 과정에서 발생할 수 있는 exception도 처리한다. 반환을 누락하면 connection이 계속 쌓여 장애로 이어질 수 있다. Java의 try-with-resources로도 정리할 수 있지만 이 강의는 JDBC의 전통적인 구조를 보여주기 위해 명시적인 close code를 사용한다.

Spring Framework와 transaction을 함께 사용할 때는 connection을 직접 `DataSource.getConnection()`으로 얻고 닫기보다 `DataSourceUtils.getConnection(dataSource)`와 `DataSourceUtils.releaseConnection(connection, dataSource)`을 사용한다. 그래야 transaction 범위에서 Spring이 관리하는 동일한 connection을 유지할 수 있다.

## DI와 OCP로 구현체 교체

Service가 concrete class가 아닌 `MemberRepository` interface에 의존하므로 configuration은 다음 구현 중 하나를 선택할 수 있다.

- `MemoryMemberRepository`
- `JdbcMemberRepository`
- `JdbcTemplateMemberRepository`
- `JpaMemberRepository`
- Spring Data JPA가 생성한 implementation

확장에는 열려 있고 기존 application logic 수정에는 닫힌 개방-폐쇄 원칙(OCP)을 DI로 실현하는 예다.

순수 JDBC 단계에서는 `SpringConfig`가 Spring Boot가 만든 `DataSource`를 주입받고 `new JdbcMemberRepository(dataSource)`를 반환하도록 조립부만 변경한다. `MemberService`는 계속 `MemberRepository` interface에 의존하므로 application logic은 수정하지 않는다. Memory 구현에서 JDBC 구현으로 기능은 확장되지만 변경은 configuration에 국한된다는 점이 OCP와 DI의 실제 효과다.

Memory repository와 달리 JDBC repository는 회원을 DB에 저장하므로 Spring application server를 재시작해도 데이터가 남는다. 단, H2 database server와 DB file이 유지되고 동일한 database에 다시 연결한다는 전제가 있다.

## 통합 테스트와 transaction

`@SpringBootTest`는 Spring container와 실제 configuration을 포함해 통합 test를 실행한다. Test에 `@Transactional`을 적용하면 test가 끝날 때 transaction을 rollback하므로 DB data가 다음 test에 남지 않는다. Application code의 transaction은 정상 완료 시 commit되는 것이 기본이므로 test에서의 rollback 동작과 구분해야 한다.

### 실행 흐름

`@SpringBootTest`가 붙은 test는 application과 같은 Spring container를 올리고 현재 configuration에 등록된 `MemberService`, `MemberRepository`, `DataSource`를 사용한다. 따라서 memory repository를 직접 생성하는 단위 test와 달리 Bean 조립, database connection, SQL 실행을 함께 검증한다.

Class에 `@Transactional`을 선언하면 각 test method가 다음 순서로 실행된다.

1. Test method 실행 전에 transaction을 시작한다.
2. 회원 저장과 조회 SQL을 같은 transaction 안에서 실행하고 결과를 검증한다.
3. Test method가 끝나면 기본적으로 rollback한다.
4. 다음 test method는 별도의 transaction에서 시작한다.

Rollback은 test가 만든 변경을 DB에 최종 반영하지 않는 것이지, 이미 존재하던 data를 삭제하는 기능은 아니다. 이전 실행이나 다른 도구가 넣은 row는 그대로 남으므로 production DB가 아닌 local 또는 test 전용 DB를 사용해야 한다. 필요해서 결과를 실제 commit해야 할 때는 `@Commit` 또는 `@Rollback(false)`를 명시할 수 있지만 test 격리가 깨지므로 의도를 분명히 해야 한다.

Identity나 sequence 값은 row rollback·삭제와 별개로 계속 증가할 수 있으므로 test에서 특정 id 숫자를 가정하지 않는다. 저장 결과를 검증할 때는 반환된 id를 다시 조회하거나 business field를 비교한다.

### Kotlin으로 작성한 통합 테스트

Java 강의의 field injection을 그대로 옮기면 Kotlin에서는 `@Autowired lateinit var`를 사용할 수 있다. 그러나 Spring 공식 Kotlin 문서는 JUnit Jupiter의 constructor injection을 활용해 dependency를 `val`로 선언하는 방법도 안내한다. 필수 dependency가 생성 시점에 확정되고 `lateinit` 초기화 위험이 없어 실무 코드에는 constructor injection이 더 명확하다.

다음 예제는 Kotlin으로 전환한 `Member`가 `Member(name = "spring")`처럼 생성되고 `findOne()`이 `Member?`를 반환한다고 가정한다.

```kotlin
import org.assertj.core.api.Assertions.assertThat
import org.assertj.core.api.Assertions.assertThatThrownBy
import org.junit.jupiter.api.Test
import org.springframework.boot.test.context.SpringBootTest
import org.springframework.test.context.TestConstructor
import org.springframework.transaction.annotation.Transactional

@SpringBootTest
@Transactional
@TestConstructor(autowireMode = TestConstructor.AutowireMode.ALL)
class MemberServiceIntegrationTest(
    private val memberService: MemberService,
) {

    @Test
    fun `회원 가입 후 조회된다`() {
        val member = Member(name = "spring")

        val savedId = memberService.join(member)
        val foundName = memberService.findOne(savedId)?.name

        assertThat(foundName).isEqualTo(member.name)
    }

    @Test
    fun `중복 회원 가입은 실패한다`() {
        val first = Member(name = "spring")
        val second = Member(name = "spring")
        memberService.join(first)

        assertThatThrownBy {
            memberService.join(second)
        }
            .isInstanceOf(IllegalStateException::class.java)
            .hasMessage("이미 존재하는 회원입니다.")
    }
}
```

Kotlin에서는 test function 이름을 backtick으로 감싸 문장처럼 작성할 수 있다. Java의 `Optional<Member>`를 Kotlin service에서 `Member?`로 바꿨다면 `found?.name`처럼 safe call로 조회 결과를 다룬다. `@TestConstructor`를 project 전체 기본값으로 쓰고 싶다면 `junit-platform.properties`에 다음 값을 둘 수 있다.

```properties
spring.test.constructor.autowire.mode=all
```

이 설정을 사용하면 개별 test class의 `@TestConstructor`를 생략할 수 있다.

### 단위 테스트와 통합 테스트의 역할

| 구분 | 단위 테스트 | 통합 테스트 |
|---|---|---|
| 구성 | Service와 memory/fake Repository를 직접 생성 | Spring container와 실제 Bean configuration 사용 |
| 외부 연결 | 보통 없음 | DB, transaction, SQL까지 연결 |
| 속도 | 빠름 | ApplicationContext와 DB를 올리므로 상대적으로 느림 |
| 주로 검증하는 것 | Business rule과 한 객체의 동작 | Bean 조립, infrastructure 연결과 계층 간 협력 |

Business rule은 빠른 단위 test로 촘촘하게 검증하고, 실제 configuration과 SQL이 제대로 연결되는지는 필요한 범위의 통합 test로 확인한다. 모든 test를 `@SpringBootTest`로 작성하면 실행 속도가 느려지고 business logic과 infrastructure 실패 원인을 구분하기 어려워질 수 있다.

## JdbcTemplate

JdbcTemplate은 connection 획득·반환과 exception 변환 같은 JDBC 반복 코드를 줄인다. 다만 SQL 자체는 개발자가 직접 작성한다. SQL을 명시적으로 제어하면서 boilerplate를 줄이고 싶을 때의 중간 단계다.

### 순수 JDBC에서 줄어드는 것

순수 JDBC에서는 `Connection`, `PreparedStatement`, `ResultSet`을 직접 열고 닫으며 parameter binding, exception 처리와 resource 반환을 반복했다. `JdbcTemplate`은 이 실행 절차를 template으로 제공하고, 개발자는 다음 두 가지에 집중한다.

- 실행할 SQL과 binding parameter
- 한 row를 domain object로 변환하는 `RowMapper`

즉 SQL까지 사라지는 것은 아니다. 강의는 이를 **JDBC 반복 코드는 제거하지만 SQL은 직접 작성하는 단계**로 설명한다. `spring-boot-starter-jdbc`와 datasource 설정은 순수 JDBC 단계의 것을 그대로 사용한다.

### DataSource 주입과 생성자 구성

강의의 `JdbcTemplateMemberRepository`는 `MemberRepository`를 구현하고 `DataSource`를 생성자로 받는다. 주입받은 datasource로 `JdbcTemplate`을 한 번 만들어 재사용한다.

```java
public class JdbcTemplateMemberRepository implements MemberRepository {
    private final JdbcTemplate jdbcTemplate;

    public JdbcTemplateMemberRepository(DataSource dataSource) {
        this.jdbcTemplate = new JdbcTemplate(dataSource);
    }
}
```

Spring Bean의 생성자가 하나뿐이면 `@Autowired`를 생략할 수 있다. 여러 생성자가 있는 경우에는 어떤 생성자를 사용할지 별도 지정이 필요할 수 있다.

### 조회와 RowMapper

`query`는 SQL을 실행하고 결과 row마다 `RowMapper` callback을 호출한다. Mapper는 `ResultSet`의 column을 읽어 `Member`로 바꾼다.

```java
private RowMapper<Member> memberRowMapper() {
    return (rs, rowNum) -> {
        Member member = new Member();
        member.setId(rs.getLong("id"));
        member.setName(rs.getString("name"));
        return member;
    };
}

public Optional<Member> findById(Long id) {
    List<Member> result = jdbcTemplate.query(
        "select * from member where id = ?",
        memberRowMapper(),
        id
    );
    return result.stream().findAny();
}
```

`findByName`도 같은 mapper를 재사용하고 WHERE parameter만 name으로 바꾼다. `findAll`은 `query("select * from member", memberRowMapper())`가 반환한 List를 그대로 돌려주면 된다. 강의 중 첫 test 실패는 `findById` SQL의 `?`에 대응하는 `id` argument를 빠뜨린 오류였고, integration test가 이를 즉시 찾아냈다.

### 저장과 SimpleJdbcInsert

`SimpleJdbcInsert`는 database metadata를 이용해 INSERT 구성을 줄인다. Table 이름과 generated key column인 `id`를 지정한 뒤 name 값을 전달하고 `executeAndReturnKey`로 DB가 생성한 id를 받는다. 이 저장 경로에서는 INSERT SQL도 직접 적지 않지만, JdbcTemplate의 일반 조회·수정에서는 여전히 SQL을 작성한다.

```java
SimpleJdbcInsert jdbcInsert = new SimpleJdbcInsert(jdbcTemplate)
    .withTableName("member")
    .usingGeneratedKeyColumns("id");

Number key = jdbcInsert.executeAndReturnKey(parameters);
member.setId(key.longValue());
```

Parameter map이나 property source의 이름은 database column 이름과 맞아야 한다.

### 구현체 교체와 통합 테스트

Configuration에서 `MemberRepository` Bean만 `new JdbcTemplateMemberRepository(dataSource)`로 바꾼다. Service와 Controller는 interface에 의존하므로 수정하지 않는다. 앞서 만든 `@SpringBootTest` 통합 test를 다시 실행하면 Bean 조립부터 SQL과 실제 DB 연결까지 한 번에 검증할 수 있다. 강의처럼 H2 server 방식으로 실습한다면 test 실행 중 DB server도 켜져 있어야 한다.

수동으로 application을 실행하고 회원 가입 화면을 반복 조작하는 대신 자동화된 test를 재실행하면 parameter 누락이나 복사·붙여넣기 실수를 빠르게 찾을 수 있다. 이는 JdbcTemplate 사용법 자체와 함께 이 강의가 강조하는 핵심이다.

### Kotlin 보조 예제

다음은 강의의 Java 구조를 Kotlin으로 옮긴 보조 예제다. 강의의 핵심인 SQL, `RowMapper`, generated key와 repository 교체 흐름은 동일하다. 예제는 immutable `data class Member(val id: Long? = null, val name: String)`와 `Member?` 반환 계약을 가정한다.

```kotlin
class JdbcTemplateMemberRepository(
    dataSource: DataSource,
) : MemberRepository {
    private val jdbcTemplate = JdbcTemplate(dataSource)
    private val insertMember = SimpleJdbcInsert(dataSource)
        .withTableName("member")
        .usingGeneratedKeyColumns("id")

    private val memberRowMapper = RowMapper<Member> { rs, _ ->
        Member(
            id = rs.getLong("id"),
            name = rs.getString("name"),
        )
    }

    override fun save(member: Member): Member {
        val generatedId = insertMember.executeAndReturnKey(
            mapOf("name" to member.name),
        ).toLong()
        return member.copy(id = generatedId)
    }

    override fun findById(id: Long): Member? =
        jdbcTemplate.query(
            "select * from member where id = ?",
            memberRowMapper,
            id,
        ).firstOrNull()

    override fun findByName(name: String): Member? =
        jdbcTemplate.query(
            "select * from member where name = ?",
            memberRowMapper,
            name,
        ).firstOrNull()

    override fun findAll(): List<Member> =
        jdbcTemplate.query("select * from member", memberRowMapper)
}
```

Java의 `Optional<Member>`와 `stream().findAny()`는 Kotlin에서는 보통 nullable type인 `Member?`와 `firstOrNull()`로 표현한다. Mutable domain model을 유지한다면 `copy` 대신 생성된 id를 property에 설정할 수도 있지만, immutable model에서는 새 object를 반환하는 방식이 상태 변화를 추적하기 쉽다.

## JPA

JDBC에서 JdbcTemplate으로 이동하면 resource 관리와 반복 코드는 크게 줄지만 SQL은 여전히 개발자가 작성한다. JPA는 한 단계 더 나아가 object와 relational table 사이의 mapping을 바탕으로 INSERT, UPDATE, DELETE와 단순 SELECT SQL을 생성한다. 개발자는 table과 column 중심의 처리보다 entity와 object 관계를 중심으로 application을 설계할 수 있다.

JPA는 Java 진영의 ORM 표준 interface이고 Hibernate는 Spring Boot에서 널리 사용하는 구현체다. ORM은 object와 relational database table을 mapping한다는 뜻이다. JPA가 최종적으로 DB와 통신할 때는 여전히 SQL이 실행되므로 SQL 지식과 생성 SQL 확인은 필요하다.

### Dependency와 기본 설정

강의에서는 JDBC starter를 `spring-boot-starter-data-jpa`로 교체한다. 이 starter에는 JPA와 JDBC 관련 dependency가 함께 들어온다. 다음 설정으로 Hibernate가 실행하는 SQL을 보고, 이미 만든 schema를 사용하도록 자동 DDL 생성을 끈다.

```properties
spring.jpa.show-sql=true
spring.jpa.hibernate.ddl-auto=none
```

`ddl-auto=create` 같은 설정은 entity mapping에서 table을 생성할 수 있지만 기존 data에 영향을 줄 수 있으므로 환경에 맞게 의도적으로 선택한다. 강의 실습은 이미 만든 member table을 사용하므로 `none`으로 시작한다.

### Entity mapping

`@Entity`가 붙은 class는 JPA가 관리하는 entity가 된다. `@Id`는 primary key property를 지정하고, `@GeneratedValue(strategy = GenerationType.IDENTITY)`는 INSERT 시 DB가 id를 생성하는 identity 전략을 사용한다.

```java
@Entity
public class Member {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;
}
```

Property 이름과 column 이름이 같으면 기본 mapping을 사용할 수 있다. 다르면 `@Column(name = "user_name")`처럼 실제 column 이름을 지정한다. 이 mapping 정보가 있어야 JPA가 SQL을 만들고 DB row를 entity로 복원할 수 있다.

Spring Boot 3.0 이상에서는 persistence annotation package가 `javax.persistence`에서 `jakarta.persistence`로 바뀌었다. 반면 `javax.sql.DataSource`는 그대로다.

### EntityManager로 저장하고 조회하기

`EntityManager`는 JPA 작업의 중심 API다. Spring Boot는 datasource와 JPA 설정을 이용해 EntityManager를 사용할 수 있도록 구성하고, Repository는 이를 주입받는다.

```java
public Member save(Member member) {
    entityManager.persist(member);
    return member;
}

public Optional<Member> findById(Long id) {
    Member member = entityManager.find(Member.class, id);
    return Optional.ofNullable(member);
}
```

`persist(member)`를 호출하면 JPA가 INSERT SQL을 만들고, identity 전략으로 생성된 id를 managed entity에 반영한다. Primary key 조회는 `find(EntityType, id)`로 처리한다. Memory repository에 object를 저장하고 찾는 것과 비슷한 호출 형태지만, 실제로는 Hibernate가 mapping을 해석해 SQL을 실행한다.

### JPQL로 조건 조회하기

Primary key가 아닌 name 조건이나 전체 목록처럼 더 일반적인 조회에는 이 강의 단계에서 JPQL을 작성한다. JPQL은 table이 아니라 entity와 property를 대상으로 작성되고, JPA 구현체가 database SQL로 변환한다.

```java
List<Member> result = entityManager.createQuery(
        "select m from Member m where m.name = :name",
        Member.class
    )
    .setParameter("name", name)
    .getResultList();
```

여기서 `Member`는 table 이름이 아니라 entity type이고 `m.name`도 entity property다. SQL처럼 column을 꺼낸 뒤 다시 object에 mapping하지 않고 `Member` object 목록을 직접 받는다. 이 단계에서는 `findAll`과 `findByName`에 JPQL이 필요하지만, 다음 단계인 Spring Data JPA에서는 method 이름으로 이 query 구현도 더 줄일 수 있다.

### Transaction과 구현체 교체

JPA의 저장·변경 작업은 transaction 안에서 실행해야 한다. 강의는 business 작업의 경계인 Service 계층에 `@Transactional`을 적용한다. Repository의 단일 method보다 회원 가입 전체를 하나의 작업으로 묶을 수 있기 때문이다.

Configuration에서는 `MemberRepository` Bean만 `JpaMemberRepository(entityManager)`로 교체한다. Service와 Controller는 계속 interface를 사용하므로 변경하지 않는다. 기존 `@SpringBootTest` 통합 test를 실행하면 entity mapping, Bean 조립, transaction과 실제 DB SQL을 함께 확인할 수 있다. Test의 `@Transactional`은 기본 rollback이고, 결과 확인을 위해 commit을 강제하면 DB에 data가 남는다는 차이도 구분한다.

### Kotlin 보조 예제

다음 코드는 강의의 JPA 구조를 Kotlin으로 옮긴 보조 예제다. 강의의 핵심인 entity mapping, EntityManager, JPQL과 transaction 경계는 그대로 유지한다.

```kotlin
import jakarta.persistence.Column
import jakarta.persistence.Entity
import jakarta.persistence.GeneratedValue
import jakarta.persistence.GenerationType
import jakarta.persistence.Id

@Entity
class Member(
    @Column(name = "name")
    var name: String,
) {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    var id: Long? = null
        protected set
}
```

새 entity는 아직 DB에 저장되지 않았으므로 id를 `Long?`으로 표현한다. 저장 후 JPA가 생성된 id를 채운다. Kotlin class는 기본적으로 `final`이고 primary constructor가 zero-argument constructor가 아니므로, JPA가 entity를 생성하거나 proxy로 확장할 수 있게 project의 Kotlin version에 맞는 `kotlin-jpa` compiler plugin 구성을 확인한다. Spring Service의 proxy에는 `kotlin-spring` plugin을 사용한다.

```kotlin
class JpaMemberRepository(
    private val entityManager: EntityManager,
) : MemberRepository {

    override fun save(member: Member): Member {
        entityManager.persist(member)
        return member
    }

    override fun findById(id: Long): Member? =
        entityManager.find(Member::class.java, id)

    override fun findByName(name: String): Member? =
        entityManager.createQuery(
            "select m from Member m where m.name = :name",
            Member::class.java,
        )
            .setParameter("name", name)
            .resultList
            .firstOrNull()

    override fun findAll(): List<Member> =
        entityManager.createQuery(
            "select m from Member m",
            Member::class.java,
        ).resultList
}
```

Java의 `Optional<Member>`는 Kotlin에서 보통 `Member?`로 표현한다. `Member.class`는 `Member::class.java`, getter 호출은 property 접근, `stream().findAny()`는 `firstOrNull()`로 옮길 수 있다. JPA entity는 persistence lifecycle과 proxy 요구사항이 있으므로 일반 DTO처럼 무조건 immutable `data class`로 바꾸기보다, entity 역할에 맞춘 class와 제한된 mutable property를 사용하는 편이 이해하기 쉽다.

```kotlin
@Service
@Transactional
class MemberService(
    private val memberRepository: MemberRepository,
)
```

`@Transactional`을 Service에 두면 회원 가입 과정의 중복 검사와 저장을 하나의 transaction 경계로 묶는다. Kotlin에서는 Spring proxy가 class를 확장할 수 있도록 `kotlin-spring` plugin 구성이 필요하다.

## Spring Data JPA

Spring Data JPA는 JPA를 대체하는 ORM이 아니라 JPA 위에서 Repository 개발을 편리하게 만드는 Spring framework다. Hibernate가 entity mapping과 SQL 생성을 담당하고, Spring Data JPA는 반복되는 Repository 구현과 단순 query 작성을 줄인다. 따라서 JPA의 entity lifecycle, transaction과 생성 SQL을 먼저 이해한 뒤 사용하는 것이 중요하다.

### Interface만으로 Repository 만들기

강의에서는 구현 class 없이 interface만 선언한다.

```java
public interface SpringDataJpaMemberRepository
        extends JpaRepository<Member, Long>, MemberRepository {

    Optional<Member> findByName(String name);
}
```

`JpaRepository<Member, Long>`의 첫 type은 관리할 entity, 두 번째 type은 entity primary key의 type이다. Interface가 다른 interface를 받을 때는 `implements`가 아니라 `extends`를 사용하며 여러 interface를 함께 상속할 수 있다.

Application 시작 시 Spring Data JPA가 이 interface를 발견하면 proxy 기반 구현 object를 만들고 Spring Bean으로 등록한다. 개발자가 `SpringDataJpaMemberRepositoryImpl` 같은 구현 class나 별도의 `@Bean` 등록을 만들지 않아도 injection할 수 있는 이유다.

```text
Repository interface 발견
        ↓
Spring Data JPA가 구현 object 생성
        ↓
Spring Bean으로 등록
        ↓
Service 또는 configuration에 injection
```

실제 DB 작업에는 기존 JPA와 Hibernate가 사용되므로 integration test에서 출력되는 SQL도 JPA 단계와 같은 계열이다.

### 제공되는 공통 기능

`JpaRepository`는 반복되는 CRUD와 목록·paging 관련 API를 제공한다. 대표적으로 entity 저장, primary key 조회, 전체 조회, 삭제와 count를 직접 구현할 필요가 없다. 강의가 처음부터 `MemberRepository`의 `save`, `findById`, `findAll` signature를 비슷하게 설계한 이유도 이 단계에서 기존 application contract를 유지한 채 구현을 교체하는 흐름을 보여주기 위해서다.

Spring Data JPA가 모든 business query를 공통 API로 미리 제공할 수는 없다. 회원 이름, email이나 주문 번호처럼 domain마다 조건이 다르기 때문이다.

### Method 이름으로 query 생성하기

Spring Data JPA는 정해진 naming rule에 따라 Repository method를 해석하고 query를 생성한다.

```java
Optional<Member> findByName(String name);
```

이 선언은 개념적으로 다음 JPQL에 대응한다.

```jpql
select m from Member m where m.name = :name
```

`findByNameAndId`처럼 property와 조건 keyword를 조합할 수도 있다. Method 이름, parameter와 return type을 분석해 구현하기 때문에 entity에 실제로 존재하는 property 이름을 정확히 사용해야 한다. 단순 조건 조회는 interface 선언으로 끝나지만, query가 복잡해질수록 method 이름만으로 표현하기보다 다른 query 수단을 선택한다.

### Kotlin에서 사용할 때

Custom Repository가 Java 강의처럼 `Optional<Member>` contract를 유지한다면 `JpaRepository<Member, Long>`과 함께 상속할 수 있다. Kotlin application이 조회 결과를 `Member?`로 설계한다면 Java의 `findById(): Optional<Member>`와 return type이 충돌할 수 있으므로 같은 interface에 억지로 합치지 않는다.

가장 단순한 Kotlin 구성은 Spring Data JPA Repository 자체를 application Repository로 사용하는 것이다.

```kotlin
interface MemberRepository : JpaRepository<Member, Long> {
    fun findByName(name: String): Member?
}
```

Domain port가 `Member?` 같은 독립 contract를 반드시 유지해야 한다면 Spring Data interface와 port를 분리하고 adapter class가 둘 사이를 변환하는 구조를 선택할 수 있다. 어느 방식을 쓰든 Kotlin이라고 별도의 persistence 표준을 사용하는 것은 아니며 JPA·Hibernate·Spring Data JPA 계층은 그대로다.

### 복잡한 query와 기술 조합

Spring Data JPA는 편의 layer이므로 JPA 자체의 학습을 대신하지 않는다. 복잡한 동적 query는 Querydsl 같은 도구를 조합할 수 있고, 필요한 경우 JPA native SQL, JdbcTemplate 또는 다른 SQL 접근 기술을 함께 사용할 수도 있다. 모든 query를 method 이름으로 해결하려 하지 말고 query 특성에 맞는 도구를 선택한다.

### 통합 테스트로 구현 교체 확인

Repository를 Spring Data JPA interface로 교체한 뒤 기존 integration test를 그대로 실행해 회원 가입, 조회와 중복 회원 규칙을 검증한다. Test가 통과하면 Service의 business logic을 바꾸지 않고 Repository 구현 방식만 교체되었으며, 자동 생성된 Bean부터 Hibernate와 DB까지 연결되었음을 확인할 수 있다.
