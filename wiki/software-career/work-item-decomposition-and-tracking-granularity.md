# Jira 작업 항목의 분할 크기와 관리 비용

## Overview

작업을 작게 나누는 것은 진행과 구현을 돕지만, Jira의 스토리와 하위 작업을 지나치게 작은 단위로 등록하면 생성·상태 변경·추적에 드는 관리 비용이 커질 수 있다. 이 현업 피드백에서는 GitHub Issue 정도의 작은 구현 조각을 각각 하위 작업으로 만들기보다 페이지 정도의 결과 단위를 출발점으로 삼는 방식을 제안한다. 이는 모든 팀에 적용되는 절대 규칙이 아니라 다음 업무에서 검증할 개인 실무 지침이다.

## 피드백의 배경

`TNSP-963` 에픽의 스토리와 하위 작업이 너무 작게 나뉘었다는 피드백을 받았다. `TNSP-1179`와 같이 GitHub Issue 정도 크기의 구현 조각까지 Jira 하위 작업으로 관리하면 항목 수가 늘어나고 전체 진행 상황을 관리하기 어려워질 수 있다는 것이 핵심이었다.

대안으로는 개별 구현 조각보다 페이지 단위 정도로 하위 작업을 묶는 방안이 제시되었다.

## 핵심 구분: 구현 순서와 추적 단위

개발 과정에서는 안전한 구현을 위해 일을 작은 단계로 나눌 수 있다. 그러나 그 모든 단계를 Jira의 별도 하위 작업으로 등록해야 하는 것은 아니다.

- **구현 단위:** 개발자가 코드를 작성하고 검증하기 위해 내부적으로 나누는 작은 단계
- **추적 단위:** 팀이 담당자, 진행 상태와 완료 결과를 확인하기 위해 Jira에 표시하는 단위

이번 피드백은 구현을 크게 하라는 뜻보다, 작은 구현 단계 전부를 추적 항목으로 승격하지 말라는 조언으로 해석할 수 있다.

## 다음 Jira 작업에서 적용할 기준

새 에픽을 분해할 때는 우선 페이지나 이에 준하는 사용자 결과 단위를 하위 작업 후보로 잡는다. 이후 다음 질문으로 크기를 점검한다.

1. 이 항목이 완료되었을 때 팀원이 알아볼 수 있는 결과가 생기는가?
2. 담당자와 진행 상태를 별도로 추적할 실익이 있는가?
3. 더 작은 단계는 Jira 항목이 아니라 체크리스트나 구현 메모로 관리해도 되는가?
4. 항목 수가 늘어나면서 얻는 가시성보다 관리 비용이 더 커지지는 않는가?

페이지 단위는 출발점이지 고정 규칙이 아니다. 페이지보다 작은 작업도 독립적인 담당·검토·배포가 필요하면 별도 항목이 될 수 있고, 여러 페이지가 하나의 결과로 함께 움직인다면 더 크게 묶을 수 있다.

## 개인 운영 원칙

다음에는 먼저 팀이 확인할 결과 단위로 스토리와 하위 작업을 설계하고, 실제 코딩에 필요한 세부 단계는 작업 내부에서 나눈다. 작성 후에는 항목 하나하나가 독립적으로 추적할 가치가 있는지 확인하고, 단순 구현 절차에 가까운 항목은 상위 작업의 체크리스트로 합치는 방안을 고려한다.
