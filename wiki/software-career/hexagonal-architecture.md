## Overview

헥사고날 아키텍처(Hexagonal Architecture)는 비즈니스 기능을 UI·DB·외부 API 같은 구체 기술에서 분리하는 애플리케이션 설계 방식이다. Ports and Adapters라는 이름처럼, 애플리케이션 경계에는 목적에 맞는 계약인 포트를 두고 외부 기술과의 연결은 adapter가 맡는다. 외부 기술을 준비하지 않아도 핵심 로직을 실행·테스트할 수 있는지가 중요한 기준이다. 육각형 모양, 정해진 포트 수, 특정 폴더 구조 자체가 목표는 아니다.

## 어떤 문제를 해결하려는가

Cockburn의 원문은 UI 코드에 비즈니스 로직이 섞이거나, 애플리케이션이 특정 DB의 존재에 묶이는 문제에서 출발한다. 화면이 바뀌면 비즈니스 테스트까지 흔들리고, DB를 사용할 수 없으면 핵심 기능 개발도 막힐 수 있다.

핵심 기능을 애플리케이션의 API로 호출할 수 있게 만들면, 사람의 화면 조작 대신 테스트·배치·다른 프로그램이 같은 기능을 실행할 수 있다. DB 측도 교체 가능한 계약으로 분리하면 메모리에서 동작하는 테스트 대역을 연결할 수 있다.

원문이 강조하는 경계는 위와 아래보다 **애플리케이션의 안과 밖**이다. 기술을 사용하는 코드와 비즈니스 로직이 뒤섞이지 않도록 경계를 만들고, 독립 실행과 테스트로 그 분리를 확인한다.

## 구성 요소와 책임

| 구성 요소 | 책임 | 설정 조회 예 |
|---|---|---|
| 애플리케이션 내부 | 비즈니스 규칙과 기능 실행 | 설정이 있으면 반환하고 없으면 기본 설정 생성 |
| 입력 포트 | 외부가 실행할 수 있는 기능의 계약 | 설정 조회·기본값 생성 use case |
| 입력 adapter | 외부 요청을 입력 포트 호출로 연결 | HTTP Controller, 배치·메시지 처리기 |
| 출력 포트 | 애플리케이션이 외부에 요구하는 기능의 계약 | 설정 조회·저장 |
| 출력 adapter | 출력 계약을 특정 기술로 구현 | MongoDB 접근, 메모리 테스트 대역 |
| 조립 코드 | 실제 구현을 선택해 객체 연결 | 생성자에 저장 adapter를 주입하는 설정 |

입력·출력은 누가 호출을 시작하는지를 기준으로 이해한다. DB 조회 결과가 안으로 돌아오더라도 애플리케이션이 조회를 시작한다면 출력 측 대화다. 포트 자체와 Kotlin `interface`의 관계는 [포트 상세 문서](hexagonal-architecture-ports.md)에서 다룬다.

## 호출 흐름과 코드 의존관계는 다르다

다음은 우아한형제들 설정 조회 사례를 바탕으로 단순화한 실행 흐름이다.

```text
HTTP 요청
  → Controller
  → 설정 조회 use case
  → 설정 조회·저장 포트 호출
  → DB Adapter
  → DB
```

실행 중에는 내부에서 바깥 DB 기능을 호출하지만, 내부 코드가 구체 DB adapter에 직접 의존하도록 만들 필요는 없다. 내부에 필요한 조회·저장 계약을 정의하고 바깥 adapter가 구현한다.

```text
코드에서 참조하는 방향

Controller       → 입력 계약 / use case
use case         → 내부 모델 + 출력 계약
DB Adapter       → 출력 계약 + DB 접근 기술
조립 코드         → 연결할 실제 구현들
```

예를 들어 서비스가 `MongoTemplate`을 직접 받아 DB 세부 동작을 수행하면 기술 의존이 서비스까지 들어온다. 출력 포트만 사용하게 하면 서비스는 비즈니스 기능을 실행하는 데 필요한 조회·저장 능력에 의존한다. 실제 저장 기술을 선택하는 코드는 외부 조립 영역에 둔다.

이 의존관계의 분리는 [SOLID의 DIP](../spring/spring-object-oriented-design-and-solid.md)와 [AppConfig의 객체 조립](../spring/spring-appconfig-ioc-di.md)을 공부한 뒤 연결해서 읽을 수 있다.

## Domain과 Application을 나누는 구현 사례

우아한형제들 글은 내부 모델과 규칙을 Domain에, 기능 실행을 Application에 배치한다. 기술 adapter는 Framework에, HTTP API·consumer와 구동 설정은 Bootstrap에 배치한다.

| 사례의 구분 | 주요 내용 | 읽을 때 구분할 점 |
|---|---|---|
| Domain | 비즈니스 규칙과 모델 | Spring annotation을 사용하지 않는 영역 |
| Application | use case와 출력 포트 | 해당 팀은 생산성을 고려해 서비스에 Spring annotation 사용 |
| Framework | 출력 포트의 기술 구현 | DB·외부 통신 기술별 모듈 |
| Bootstrap | 입력 측 진입점과 실행·조립 | 필요한 설정과 구현을 선택해 애플리케이션 구동 |

이는 해당 프로젝트의 구현 선택이다. Domain·Application의 세부 구분, Framework·Bootstrap이라는 이름, Gradle 멀티 모듈 구성이 Cockburn 원문의 고정 규격은 아니다. 원문은 고립된 실행과 목적 중심의 포트·adapter를 설명한다. 특정 모듈 템플릿과 아키텍처 개념을 구분해서 읽는다.

## 우아한형제들 사례의 개발 순서

글의 기능 예는 설정을 조회하고, 없으면 기본 설정을 저장해 반환하는 흐름이다.

1. 내부에서 사용할 설정 모델과 기본 설정 동작을 정의한다.
2. `MerchantSettingRetrieveUseCase`로 기능을 표현한다.
3. `MerchantSettingManagementOutputPort`로 필요한 조회·저장 기능을 정의한다.
4. use case 구현을 만들고 출력 포트의 테스트 대역으로 검증한다.
5. 출력 포트를 구현하는 DB adapter를 만들고 기술 연동을 검증한다.
6. Controller에서 use case를 호출하도록 연결하고 전체 흐름을 검증한다.

이 목록은 원문의 개발 단계를 학습용으로 묶어 요약한 것이다. Controller부터 DB까지 모든 환경이 갖춰져야 핵심 기능을 테스트할 수 있는 구조와 비교해 읽는다.

원문은 개념 설명을 위한 발췌 코드이고 미구현 부분도 포함한다. 오래된 의존성 버전·설정이나 코드 조각을 현재 프로젝트의 실행 가능한 템플릿으로 복사하지 않는다. 이 wiki에서도 해당 프로젝트를 빌드하거나 테스트를 재현하지 않았다.

## 테스트와 변경에서 확인할 것

- 핵심 비즈니스 기능을 UI·실제 DB 없이 실행할 수 있는가?
- 같은 입력 포트에 테스트 실행기나 다른 진입점을 연결할 수 있는가?
- 출력 포트에 실제 adapter 대신 테스트 대역을 연결할 수 있는가?
- 기술 내부의 변경이 포트의 업무상 계약을 바꾸지 않을 때, 내부 로직도 유지되는가?

Cockburn 원문과 AWS 가이드를 함께 읽어 도출한 확인 질문이다. 외부 변경이 항상 adapter에만 머문다는 보장은 아니다. 업무 요구사항이나 계약 자체가 바뀌면 내부 로직과 포트도 함께 바뀔 수 있다.

실제 DB·외부 서비스와의 연결을 확인하는 테스트 역시 필요하다. 우아한형제들 사례는 use case 테스트와 DB adapter 검증, 통합 테스트를 구분한다. 테스트 대역으로 핵심 기능을 검증했다는 사실만으로 기술 연동까지 검증됐다고 보지 않는다.

## 적용 기준과 비용

AWS 가이드는 같은 비즈니스 로직을 사용하는 여러 클라이언트, UI·DB의 기술 교체, 다양한 입력·출력과 독립 테스트의 필요를 적용 조건으로 제시한다. 추가 adapter 코드가 이점을 주지 못하면 유지할 계층만 늘어날 수 있고, 복잡성과 지연 가능성도 고려해야 한다.

우아한형제들 역시 경계마다 객체를 변환하는 반복 작업, 비슷한 데이터 클래스, 세분화된 설정, 늘어나는 출력 포트 인터페이스를 고민으로 기록한다. 해당 팀은 영역마다 필요한 값과 표현이 달라 별도 모델을 유지했으며, 포트가 기계적으로 늘지 않도록 use case와 계약을 팀에서 검토하는 방향을 제안한다.

따라서 먼저 격리할 기술 의존성과 보호할 비즈니스 규칙을 정한다. 코드·DTO·interface가 많아졌다는 사실만으로 구조가 좋아졌다고 판단하지 않는다.

## 카카오페이 사례: 외부 연동이 많다고 항상 적합하지는 않다

카카오페이 홈 서버는 여러 외부 API의 데이터를 조합해 화면 응답을 만드는 역할을 맡았다. 외부 변경을 막기 위해 연동 부서와 표준 API 스펙을 정하는 동시에 헥사고날 아키텍처와 멀티 모듈을 적용했다.

하지만 작성자는 다음 조건에서 구조의 효용이 줄었다고 설명한다.

- 표준 연동 스펙이 이미 외부 변경을 줄여, 별도 아키텍처로 얻는 추가 이익이 작아졌다.
- 보호할 독립적인 도메인보다 외부 데이터의 조합·표현 역할이 컸다.
- 출력 포트를 외부 클라이언트 응답 기준으로 설계하면서 외부 변경이 포트까지 전파됐다.
- 신규 기능마다 포트·DTO·adapter와 변환 로직을 함께 바꿔야 했고 설명·탐색 비용도 늘었다.

해당 팀은 단일 모듈과 관심사 중심 패키지로 정리하면서 일부 포트와 변환을 통합했다. 그렇다고 모든 경계를 제거하지는 않았으며, Controller와 외부 연동 측의 DTO 분리는 유지했다.

이는 특정 홈 서버의 도입·제거 경험이다. 외부 연동 수가 많으면 반드시 헥사고날 아키텍처가 좋다거나, 반대로 외부 연동이 많으면 사용할 수 없다는 규칙으로 일반화하지 않는다. 우아한형제들 사례와의 선택 차이도 원칙의 사실관계 충돌이 아니라 업무·변경·재사용 조건의 차이로 읽는다.

카카오페이 글의 코어 모듈 재사용 조건 역시 해당 작성자의 판단 기준이다. Cockburn 원문이 입력 adapter의 교체와 고립 테스트를 강조한다는 사실과 구분한다. 여러 배포 모듈에서 코어를 재사용하는 것이 아키텍처 정의의 필수 조건이라고 바꾸어 해석하지 않는다.

## 도입 전에 확인할 질문

아래는 원문·AWS 가이드·국내 사례를 종합한 편집상의 판단 질문이다.

1. 실제로 보호할 비즈니스 규칙과 업무상 계약을 설명할 수 있는가?
2. 그 계약을 특정 DB나 외부 응답 DTO를 복사하지 않고 정의할 수 있는가?
3. 독립 테스트나 여러 진입점에서의 사용이 현재 문제를 줄이는가?
4. 기존 연동 계약이나 더 단순한 분리만으로도 필요한 보호를 얻는가?
5. 유지할 adapter·변환·설정 비용보다 얻는 이익이 큰가?
