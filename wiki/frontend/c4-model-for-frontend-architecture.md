# 프런트엔드 아키텍처를 위한 C4 모델

## Overview

C4 모델은 하나의 거대한 다이어그램에 모든 정보를 담는 대신, 독자와 목적에 맞춰 시스템을 서로 다른 상세 수준으로 확대·축소해 설명한다. 프런트엔드에서는 상위 수준의 시스템 컨텍스트와 컨테이너를 그대로 사용하고, 하위 수준의 컴포넌트와 코드는 각각 모듈과 UI 분해로 해석하면 제품 화면과 코드 구조 사이를 더 명확하게 연결할 수 있다.

## 하나의 다이어그램보다 여러 확대 수준이 필요한 이유

아키텍처 다이어그램의 독자는 같은 정보를 원하지 않는다. 프로덕트 매니저는 시스템 전체와 외부 상호작용을 보고 싶어하지만, 프런트엔드 개발자는 UI 내부의 구성 요소와 관계에 더 관심이 있을 수 있다. C4 모델은 이런 차이를 네 가지 수준으로 분리해 각 독자에게 필요한 범위만 보여준다.

| 수준 | 기본 C4 관점 | 주요 내용 | 주 독자 |
|------|---------------|-----------|---------|
| 레벨 1 | 시스템 컨텍스트 | 시스템 경계, 사용자, 외부 시스템과의 상호작용 | 기술 배경이 없는 이해관계자를 포함한 전체 팀 |
| 레벨 2 | 컨테이너 | 웹 애플리케이션, SPA, 모바일 앱, API, 데이터베이스와 기술 선택 | 기술 담당자 |
| 레벨 3 | 컴포넌트 | 컨테이너를 이루는 주요 구성 요소 | 해당 애플리케이션을 다루는 개발자 |
| 레벨 4 | 코드 | 클래스, 함수, 객체와 세부 구현 관계 | 복잡하거나 중요한 구현을 다루는 개발자 |

레벨이 내려갈수록 실제 코드에 가까워진다. 반대로 모든 컴포넌트를 레벨 4로 문서화하면 유지 비용이 커지므로, 세부 코드 다이어그램은 중요하거나 복잡한 부분에 한정하고 가능한 경우 소스 코드에서 자동 생성하는 편이 적합하다.

## 프런트엔드에 맞춘 레벨 3: 컴포넌트를 모듈로 보기

C4의 컴포넌트와 UI 컴포넌트는 의미가 다르기 때문에 프런트엔드에서는 레벨 3의 명칭을 모듈로 바꾸면 혼동이 줄어든다. 이때 모듈은 애플리케이션의 최상위 UI 구성 단위다.

모듈은 흔히 `/dashboard`, `/settings`, `/login` 같은 최상위 경로와 대응하지만, URL 경로가 모듈의 필수 조건은 아니다. 전용 경로가 없는 장바구니처럼 독립적인 책임과 UI 영역을 가진 기능도 하나의 모듈이 될 수 있다. 중요한 기준은 폴더나 라우트 이름 자체가 아니라 사용자가 인식하는 상위 기능과 책임의 경계다.

## 프런트엔드에 맞춘 레벨 4: UI 분해

현대적인 컴포넌트 기반 프런트엔드에서는 UML 클래스 다이어그램만으로 UI 구조를 설명하기 어렵다. 따라서 레벨 4를 특정 모듈의 UI 분해로 바꾸고 다음 세 종류의 구성 요소를 표시할 수 있다.

- 스크린: 모듈 안의 독립적인 화면이다. 설정 모듈의 개인정보, 멤버, 통합, 결제 설정 화면처럼 하위 경로와 대응할 수 있다.
- 기능: 여러 하위 컴포넌트를 포함하고 자체 폴더가 필요할 정도로 복잡한 큰 UI 단위다.
- 컴포넌트: 버튼, 표, 폼 요소, 아이콘처럼 모듈 전체 또는 특정 스크린·기능에서 사용하는 UI 구성 요소다.

이 계층은 화면에 보이는 구조와 코드의 구성 위치를 연결한다. 새 UI 요소가 어느 모듈과 스크린에 속하는지, 독립 기능으로 승격할 만큼 복잡한지, 공유 컴포넌트인지 판단하는 공통 언어로 사용할 수 있다.

## 실무 적용 순서

먼저 여러 직군과 함께 레벨 1에서 시스템 경계와 외부 참여자를 합의하고, 레벨 2에서 프런트엔드가 다른 애플리케이션·API·데이터 저장소와 맺는 관계를 표시한다. 그 다음 프런트엔드 팀이 레벨 3에서 최상위 UI 모듈을 나누고, 복잡한 모듈만 골라 레벨 4의 스크린·기능·컴포넌트 구조로 분해한다.

명칭은 조직의 기존 용어에 맞게 바꿀 수 있다. 핵심은 C4 용어를 기계적으로 유지하는 것이 아니라, 각 확대 수준이 서로 다른 질문에 답하도록 만들고 상위 시스템 경계에서 실제 UI 구조까지 추적 가능한 지도를 제공하는 것이다.
