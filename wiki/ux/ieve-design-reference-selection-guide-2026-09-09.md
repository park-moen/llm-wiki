## Overview

디자이너가 아닌 사람이 디자인 시안을 이끌 때는 직접 멋진 화면을 그리는 능력보다 **사용자 문제, 정보 우선순위, 참고할 pattern과 검증 조건을 문서로 분명하게 전달하는 능력**이 중요하다. 레퍼런스는 취향을 보여주는 사진첩이 아니라 판단의 근거다. 화면이 해결할 문제를 먼저 정의하고, 실제 서비스에서 해결 방식을 찾아, 가져올 점과 제외할 점을 구분한 뒤 Claude가 실행할 수 있는 시안 가이드로 바꾼다.

## 시안 가이드는 무엇을 정하는 문서인가

시안 가이드는 완성된 상세 설계서가 아니다. 누가 시안을 만들더라도 엉뚱한 방향으로 가지 않도록 **문제와 선택 범위**를 고정하는 문서다. 최소한 다음 질문에 답해야 한다.

- 누가 어떤 상황에서 이 화면을 사용하는가?
- 사용자가 가장 먼저 알아야 할 정보는 무엇인가?
- 이 화면에서 반드시 끝내야 하는 행동은 무엇인가?
- 어떤 레퍼런스의 어느 해결 방식을 참고하는가?
- 무엇은 가져오지 않으며, 그 이유는 무엇인가?
- 실제 data, mobile과 오류 상태에서도 동작하는가?
- 시안이 좋아졌다고 판단할 기준은 무엇인가?

색상과 모서리 반경부터 정하면 논의가 취향 싸움으로 흐르기 쉽다. 사용자 행동과 정보 구조를 먼저 정한 뒤 시각 요소를 선택한다.

## 1. 화면 이름을 사용자 문제로 바꾼다

`참가기업 페이지`, `결제 화면`처럼 화면 이름만 적으면 필요한 형태를 알기 어렵다. 사용자, 행동, 규모와 제약을 한 문장으로 바꾼다.

```text
나쁜 정의
참가기업 목록을 세련되게 만든다.

좋은 정의
관람객이 품질과 비율이 제각각인 참가기업 logo 200개에서
관심 기업을 빠르게 찾고 상세 정보로 이동할 수 있어야 한다.
```

이 단계에서 시각적 취향은 잠시 미룬다. 다음 항목만 먼저 적는다.

| 항목 | 작성할 내용 |
|---|---|
| 사용자 | 이 화면을 가장 자주 쓰는 사람 |
| 핵심 행동 | 화면에서 완료해야 하는 한 가지 행동 |
| 우선 정보 | 첫눈에 보여야 하는 정보 |
| 실제 규모 | 항목 수, text 길이와 이미지 품질 |
| 사용 환경 | desktop·mobile, 현장·사무실 등 |
| 실패 비용 | 사용자가 놓치거나 잘못 선택했을 때의 영향 |

## 2. 같은 업종보다 같은 문제를 찾는다

레퍼런스를 찾을 때 `엑스포 사이트`, `쇼핑몰` 같은 장르명만 검색하지 않는다. 같은 문제를 더 잘 해결한 다른 업종까지 범위를 넓힌다.

| 해결할 문제 | 찾아볼 서비스 유형 |
|---|---|
| 항목이 많은 logo 목록 | Exhibitor directory, festival lineup, partner directory |
| Track과 시간이 겹치는 일정 | 개발자 conference timetable, 방송 편성표 |
| 여러 해의 archive | 연례 conference, award, festival의 past editions |
| 단계가 있는 신청과 결제 | Ticket 예매, e-commerce checkout |
| 운영자가 순서와 영역을 편집 | Block 기반 CMS, page builder |

한 사이트에서 모든 답을 가져오지 않는다. 정보 구조, 목록 처리, mobile 전환과 시각적 분위기를 각각 잘 해결한 사례가 다를 수 있다.

## 3. 예쁜 이미지보다 실제 동작을 본다

Pinterest와 Dribbble은 색감과 분위기를 정하는 moodboard에는 유용하다. 하지만 내용이 짧고 data가 적은 mockup만 보고 배치를 선택하면 실제 서비스에서 쉽게 무너진다.

제품 시안의 핵심 레퍼런스는 실제 운영되는 화면에서 찾는다.

- 항목이 많아졌을 때 검색·filter·pagination이 어떻게 바뀌는가
- 긴 국문·영문 text가 들어가도 hierarchy가 유지되는가
- loading, empty, error, disabled와 권한 부족 상태가 있는가
- mobile에서 어떤 정보를 숨기고 무엇을 먼저 보여주는가
- 입력 오류와 완료 결과를 사용자가 어떻게 확인하는가

국문 서비스라면 국내 사례를 별도로 본다. 한글은 라틴 문자와 글자 리듬, 행간과 자간이 달라 영문 화면을 그대로 옮겼을 때 밀도가 어색해질 수 있다. [GDWEB 선정작](https://www.gdweb.co.kr/sub/list.asp)과 [웹어워드코리아](https://www.i-award.or.kr/web/)는 한글 typography와 국내 사용자에게 익숙한 화면 구성을 살피는 출발점으로 사용할 수 있다.

## 4. 레퍼런스에서 판단 근거를 추출한다

`깔끔하다`, `요즘 느낌이다` 같은 평가는 시안을 만드는 사람이 실행할 수 없다. 레퍼런스마다 가져올 해결 방식과 제외할 요소를 구체적으로 기록한다.

```text
사이트명 / URL
해결할 문제   — 이 레퍼런스가 답하는 사용자 문제
가져올 것     — 위치, 동작, 상태와 우선순위를 구체적으로 작성
가져오지 않을 것 — 현재 제품에 맞지 않는 요소와 이유
검증할 것     — 실제 data와 mobile에서 확인할 조건
```

예시는 다음과 같다.

```text
가져올 것
- 회차 badge를 card 우상단에 둔다.
- 종료된 회차는 채도를 낮추되 text label도 함께 표시한다.

가져오지 않을 것
- Hover만으로 정보를 보여주는 방식은 mobile에서 사용할 수 없어 제외한다.
- 장식용 animation은 목록 탐색을 방해해 제외한다.

검증할 것
- 제목이 두 줄이어도 card 높이와 button 위치가 유지되는가?
- 색상을 보지 않아도 현재 회차와 종료 회차를 구분할 수 있는가?
```

레퍼런스의 외형 전체를 복사하지 않고 **문제를 해결한 원리**를 가져온다.

## 5. 시안 가이드에 결정 순서를 만든다

시안 가이드는 다음 순서로 작성하면 Claude가 표면적인 스타일보다 중요한 판단부터 처리하기 쉽다.

### A. 사용자와 목표

- 주요 사용자
- 사용 상황
- 핵심 행동
- 성공 조건

### B. 정보 우선순위

- 반드시 보여야 하는 정보
- 보조 정보
- 접거나 다음 화면으로 보낼 정보
- 가장 중요한 행동과 보조 행동

### C. 화면 구조

- header, navigation, 본문과 행동 영역의 관계
- 목록·상세·form 사이의 이동
- 반복되는 component
- desktop과 mobile에서 유지하거나 바꿀 구조

### D. 시각적 방향

- 전달해야 할 인상과 피해야 할 인상
- color, typography, spacing과 이미지 사용 원칙
- 참고할 레퍼런스와 참고할 부분
- 기존 design token 또는 component library 제약

### E. 상태와 예외

- loading, empty, error, success와 disabled
- 권한이 없거나 일부 data가 누락된 경우
- 긴 text, 깨진 이미지와 최대 data
- keyboard focus와 색상 외 상태 표현

### F. 시안 산출물

- 필요한 화면과 viewport
- 비교할 대안의 차이
- 실제 내용 사용 여부
- 검토할 사람과 결정 시점

## 6. Claude에 전달할 수 있는 시안 가이드 양식

```markdown
# 디자인 시안 가이드

## 1. 사용자와 목적
- 주요 사용자:
- 사용 상황:
- 핵심 행동:
- 성공 조건:

## 2. 화면 범위
- 포함할 화면:
- 포함하지 않을 화면:
- 기존에 유지할 구조:

## 3. 정보 우선순위
- 가장 먼저 보여야 하는 정보:
- 주요 행동:
- 보조 정보와 행동:

## 4. 레퍼런스
### Reference A — URL
- 가져올 것:
- 가져오지 않을 것:
- 해결하는 문제:

### Reference B — URL
- 가져올 것:
- 가져오지 않을 것:
- 해결하는 문제:

## 5. 시각적 방향
- 지향하는 인상:
- 피해야 할 인상:
- color·typography·spacing 원칙:
- 사용할 design token과 component:

## 6. 필수 상태
- 기본:
- loading:
- empty:
- error:
- success:
- disabled·권한 부족:

## 7. 반응형 화면과 접근성
- desktop:
- mobile:
- keyboard·focus:
- 색상 외 상태 표현:

## 8. 요청할 시안
- 서로 다른 판단을 보여주는 대안:
- 각 대안에서 설명할 trade-off:
- 실제 data와 긴 text 사용:

## 9. 승인 기준
- 사용자가 다음 행동을 바로 이해하는가?
- 실제 data에서도 배치가 유지되는가?
- 주요 상태와 오류 회복이 보이는가?
- 기존 제품 및 component와 일관적인가?
```

빈 항목을 억지로 채울 필요는 없다. 정하지 못한 내용은 Claude가 임의로 확정하도록 두지 말고 `미결정`으로 표시해 대안을 요청한다.

## 7. Claude에는 결과보다 선택지를 요청한다

첫 시안을 정답처럼 받아들이지 않는다. 서로 다른 판단이 드러나는 대안을 요청하고, 각 안의 trade-off를 설명하게 한다.

```text
같은 색상만 바꾼 시안이 아니라 정보 구조가 다른 대안을 제안한다.

- A안: 빠른 탐색과 높은 data 밀도 우선
- B안: 주요 항목의 설명과 시각적 강조 우선
- C안: mobile에서의 단순한 단계 진행 우선

각 안마다 해결하는 문제, 포기한 점과 실제 data에서 생길 위험을 설명한다.
```

선택지는 많을수록 좋은 것이 아니다. 차이를 설명하기 어려운 안은 같은 안의 장식 변형일 가능성이 크다.

## 8. 취향이 아니라 시나리오로 검토한다

`예쁘다`, `촌스럽다`만으로 시안을 고르지 않는다. 사용자가 실제로 수행할 행동과 실패 상황을 기준으로 검토한다.

```text
사용자는 첫 화면에서 무엇을 먼저 보는가?
핵심 행동을 설명 없이 찾을 수 있는가?
항목이 최대치여도 탐색할 수 있는가?
빈 data와 오류 상태에서 다음 행동을 알 수 있는가?
mobile에서 빠진 정보가 사용자 목표를 막지 않는가?
keyboard와 색상 외 단서만으로 상태를 이해할 수 있는가?
```

가능하면 시안에 실제 내용을 넣고 핵심 흐름을 직접 눌러 본다. screenshot의 완성도보다 사용자가 목적을 달성하고 오류에서 회복할 수 있는지를 먼저 확인한다.

## 자주 생기는 실패

| 실패 | 바꾸는 방법 |
|---|---|
| `세련되게`, `고급스럽게`처럼 인상만 전달 | 보여야 할 정보, 행동과 피할 pattern을 함께 적는다. |
| 레퍼런스 하나를 통째로 복사 | 레퍼런스별로 가져올 한 가지 해결 방식과 제외할 요소를 나눈다. |
| 이상적인 sample data만 사용 | 긴 text, 누락된 이미지, 빈 목록과 최대 항목 수를 넣는다. |
| 첫 시안을 바로 확정 | 정보 구조나 interaction이 다른 대안을 비교한다. |
| desktop 정상 화면만 작성 | mobile과 loading·empty·error·권한 상태를 함께 요청한다. |
| AI가 선택 이유까지 대신 결정 | AI의 제안은 후보로 보고 제품 책임자가 이유와 trade-off를 확정한다. |

## 비디자이너가 맡아야 할 책임

Claude는 레퍼런스 분류, 배치 대안, component 조합과 반복 수정을 빠르게 수행할 수 있다. 그러나 사용자 문제가 맞는지, 어떤 정보가 사업적으로 중요한지, 브랜드와 접근성 위험을 감수할 수 있는지는 팀이 판단해야 한다.

디자이너가 없다면 개발자나 제품 책임자 가운데 한 명을 **디자인 결정 책임자**로 정한다. 이 사람은 모든 화면을 직접 그리는 사람이 아니라 다음 내용을 명확하게 만드는 사람이다.

- 사용자와 핵심 행동
- 정보 우선순위
- 레퍼런스 선택 이유
- 포함·제외 범위
- 승인 기준과 남은 위험

좋은 시안 가이드는 디자인 지식을 많이 아는 척하는 문서가 아니다. **모르는 것은 미결정으로 남기고, 필요한 판단과 검증 방법을 다른 사람이 재현할 수 있게 적은 문서**다.

## 최종 확인 목록

- [ ] 화면 이름이 아니라 사용자 문제로 시작했는가
- [ ] 실제 data 규모와 사용 환경을 적었는가
- [ ] 같은 업종이 아니라 같은 문제를 해결한 사례도 찾았는가
- [ ] 레퍼런스마다 가져올 점과 제외할 점이 구체적인가
- [ ] 정보 우선순위와 주요 행동이 정해졌는가
- [ ] loading·empty·error·success와 권한 상태가 포함됐는가
- [ ] desktop과 mobile의 차이를 설명했는가
- [ ] 색상 외 상태 표현과 keyboard 사용을 확인했는가
- [ ] 대안마다 해결하는 문제와 trade-off가 다른가
- [ ] 최종 결정자와 승인 기준이 정해졌는가
