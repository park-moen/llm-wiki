# LLM 시대에도 프로그래밍을 계속 즐기는 법

> Source: https://news.hada.io/topic?id=34336
> Collected: 2026-09-28
> Published: 2026-09-27

## GeekNews summary

- 코딩은 사람이 맡고, LLM에는 계획 정리, 조사, 검토 등 주변 작업을 맡기는 방식으로 프로그래밍의 즐거움과 적당한 생산성 향상을 함께 추구할 수 있음

- 코드베이스에 대한 이해와 주도권을 유지하려면 직접 코드를 계속 작성해야 함. 모든 구현을 에이전트에 넘기면 코딩 실력이 약해지고, 생성된 코드에서 문제를 찾기도 어려워짐

- LLM과 함께 계획하되 중요한 결정은 직접 내리고, 조사도 병행해야 함. 에이전트에는 판단 대신 다음 작업과 수정할 위치, 주의점, 관련 자료를 준비하게 함

- 생성된 코드뿐 아니라 계획에도 자동 검토 주기를 적용하고, 코딩 위임은 정리 작업이나 위험이 낮은 리팩터링에 제한하는 편을 권함

- LLM을 쓸 수 없어도 직접 이어갈 작업 목록을 남기고, PR과 커밋 메시지처럼 사람에게 전달하는 글은 직접 작성해야 함

## 프로그래밍의 즐거움과 주도권 지키기

- AI 번아웃, 일자리 상실에 대한 불안, 프로젝트와 자신의 코드 품질에 대한 실망 속에서도 프로그래밍을 즐길 방법이 필요함

  - 대형 기술 기업의 최첨단 LLM에는 중대하고 정당한 윤리적 우려가 있지만, 여기서 다루는 범위는 일하는 방식임

- Sean Mcmullen의 소설 Souls in the Great Machine에서는 사람들이 부품으로 참여해 거대한 계산 장치를 구성함

  - 컴퓨터 위에서 인간이나 초인처럼 행동하는 LLM은 겉으로는 반대처럼 보이지만, 개발자가 소프트웨어 제작의 주체에서 기계의 톱니바퀴로 밀려난다는 점에서는 닮아 있음

  - 명세를 받아 LLM에 입력하고, 공급자가 줄인 토큰 할당량에 매달리는 작업 방식은 피하고 싶은 미래임

- Haskell로 생각을 표현하는 과정 자체가 즐거움의 원천일 수 있으며, 코드 생성은 그 즐거움을 위협할 수 있음

  - 언어마다 이런 즐거움의 정도가 다르다는 가정은 언어별 애호가들이 LLM 보조 개발의 미래를 다르게 보는 이유를 일부 설명할 수 있음

- 목표는 생산성이 크게 오른 것처럼 보이면서 즐거움을 잃는 것이 아니라, 직접 코딩하는 즐거움을 유지하며 생산성을 적당히 높이는 것임

  - LLM을 전혀 쓰지 않는 선택도 괜찮음

  - 실제 생산성 향상이 필요하거나 팀, 회사, 업계의 LLM 도입 흐름에서 뒤처지고 싶지 않다면 다른 활용법을 찾을 수 있음

## 코드를 계속 직접 작성해야 하는 이유

- 코드베이스의 주도권을 지키려면 적어도 일부 코드는 직접 작성해야 함

  - 모든 코드를 생성하게 두면 결국 코딩 에이전트만 다루기 편한 코드베이스가 될 수 있음

- 프로그래밍 실력은 연습하지 않으면 약해짐

  - 에이전트에 작업을 넘기는 문턱이 매우 낮아, 몇 주만 모든 코딩을 맡겨도 직접 코딩으로 돌아가기 어려워질 수 있음

- LLM은 홍보되는 수준만큼 사람이 읽기 좋은 코드를 잘 만들지 못하며, 이후에도 자신이 전담해서 수정할 코드를 만드는 데는 어느 정도 능숙함

  - 완전히 생성된 파일에 버그가 있다는 사실을 알아도, 코드가 낯설어 사람이 직접 찾기 어렵다고 느낄 수 있음

- 생산성 향상은 코딩 전체를 넘기는 대신 나머지 주변 작업을 맡기는 데서 얻을 수 있음

  - 특히 지루하고 번거로우며, 제대로 수행하기 어렵지 않고 결과를 쉽게 확인할 수 있는 작업이 적합함

## 계획은 함께 세우고, 결정은 직접 하기

- LLM을 자연어로 지시할 수 있는 기록과 정리 도구로 활용함

  - 도메인 전문가 사이의 긴 대화를 실행 가능한 할 일로 변환함

  - 사람이 테스트하고 결과를 기록하면, 결함 수정 계획으로 정리하게 함

- 계획 항목은 할 일 관리 도구나 프런트매터가 있는 Markdown 파일에 남겨 추적하게 함

  - 컨텍스트가 크더라도 가득 차면 정보를 조용히 잃어버릴 수 있음

### 중요한 결정은 LLM에 맡기지 말고 질문하게 해야 함

  - 질문을 이해하기 어렵다면 필요한 맥락이 빠졌거나, 사람이 지쳐 휴식이 필요한 상황일 수 있음

  - 같은 문제로 반복해서 돌아온다면 화면에서 벗어나 직접 생각하고, 원하는 바가 명확해진 뒤 다시 작업함

## 에이전트와 병행해서 조사하기

- 조사 작업을 맡긴 뒤 에이전트의 검색과 사고 과정을 계속 지켜보거나 다른 프로젝트의 에이전트를 띄우기보다, 검색 엔진으로 직접 병행 조사하는 편을 권함

  - 에이전트가 알게 될 내용을 적어도 대략적으로는 이해해야 함

  - 지켜보기, 다른 에이전트 실행하기, 커피 마시기 중에서는 차라리 커피를 마시는 편이 나음

- 조사 결과를 곧바로 사실로 받아들이고 계획을 세우면 기술 부채로 이어질 수 있음

  - 조사 위임의 목적은 에이전트가 모든 지식을 전달하거나 더 나은 결정을 내리게 하는 것이 아님

  - 사람이 일일이 자료를 찾아 에이전트에 전달하지 않아도 되게 하되, 모델링할 도메인은 에이전트만큼 또는 그보다 잘 이해해야 함

- 조사 결과와 사용한 자료의 링크를 기록하게 함

  - 나중에 이상한 제안을 하면 조사 결과와 근거 자료를 다시 확인하게 함

  - 에이전트가 스스로 오류를 찾지 못하더라도, 사람이 원자료를 읽고 판단할 수 있음

## 계획 이후의 코딩은 사람이 맡기

- 일반적인 코딩 하네스의 “먼저 계획하고, 구현은 에이전트에게 맡기기” 대신, 함께 계획한 뒤 사람이 직접 코딩함

- 에이전트에는 구현에 필요한 준비 작업을 맡김

  - 코드베이스를 조사하고 현재 할 일을 알려줌

  - 수정해야 할 위치를 모으고 잠재적 함정을 짚음

  - 관련된 사전 조사 내용을 상기시킴

- 명확하고 잘 준비된 작업을 받으면 전체 계획을 계속 신경 쓰지 않고 현재 구현에 집중할 수 있음

  - 에이전트에 사람이 맞추는 대신, 이미 잘 맞는 자신의 작업 방식 주위에 에이전트를 배치함

  - 덜 즐기는 부수 작업을 넘겨 프로세스의 번거로움 없이 애자일과 비슷한 작업 흐름을 만들 수 있음

- 이 방식은 즐거움과 코드 이해를 함께 유지하는 데 도움이 됨

  - 좋아하는 프로그래밍을 계속할 수 있음

  - 코드베이스 상태를 파악하고, 예상치 못한 생성 코드나 세션 중 맥락 상실을 피할 수 있음

  - 에이전트가 잘못된 계획을 오래 실행하기 전에 사람이 구현하면서 문제를 발견할 수 있음

  - 실력을 유지하고 계속 다듬을 수 있음

## 코딩을 위임해도 좋은 경우와 추상화의 함정

- 코딩 에이전트는 정리, 작은 작업, 반복 작업, 위험이 낮은 리팩터링에 적합함

  - 남겨 둔 `FIXME` 처리, 흥미로운 세 가지 경우를 구현한 뒤 유사한 나머지 일곱 가지 완성하기 등이 가능함

  - 구상해 둔 모듈 재구성과 벤치마크, 유지보수가 중단된 라이브러리를 더 나은 대안으로 교체하는 작업도 활용 대상임

  - 복잡한 무언가를 처음부터 설계하는 작업은 적합하지 않을 가능성이 큼

- 시간이 부족하고 남은 할 일이 명확하며 위험이 낮다면, 총괄 에이전트에 마무리를 맡길 수도 있음

  - 운이 좋으면 다음 날 완성된 기능을 받을 수 있지만, 대부분의 코딩은 직접 해야 함

- 비슷한 구현을 여러 개 복제하려 한다면 먼저 추상화 가능성을 검토해야 함

  - 실제로 필요한 것은 `lens`나 다른 `optic`, 또는 `Traversable` 같은 널리 쓰이는 타입 클래스의 인스턴스일 수 있음

  - LLM은 이런 구조를 알아보지 못하고 대량의 코드를 복사하기 쉬우므로, 사람이 가독성과 합리적인 구조를 추구해야 함

- 에이전트가 호출 체인 전체를 훑어 수정 위치를 잘 찾아주더라도, 지나친 결합과 코드 구성을 돌아봐야 함

  - 코드 조사를 위해 반드시 LLM이 필요할 정도라면 코드베이스의 조직 방식 자체가 좋지 않을 수 있음

## 코드와 계획 모두에 자동 검토 주기 적용하기

- 생성적 적대 신경망(GAN) 의 생성기와 판별기처럼, 결과를 만드는 역할과 평가하는 역할을 나누는 아이디어를 LLM 작업에도 적용함

  - 생성기만 사용할 때보다 나은 결과를 얻는 이런 일반적인 접근 자체는 새로운 것이 아님

- LLM이 만든 산출물은 자동 검토 주기를 거치기 전에는 받아들이거나 읽지 않는 방식을 권함

  - 생성 코드는 구현 에이전트가 넘겼을 때가 아니라, 검토 에이전트가 더 이상 문제를 찾지 않을 때 사람이 읽을 준비가 된 것임

  - 계획도 같은 방식으로 검토해야 함

  - 예를 들어 일곱 번째 할 일에서 만들 함수를 두 번째 할 일에서 리팩터링하도록 계획한 논리적 오류를 사람이 일일이 찾는 것은 피곤한 작업임

- 직접 작성한 코드에 대한 에이전트 검토도 도움이 될 수 있음

  - 사소한 지적이나 Haddock 문서를 불필요하게 늘리라는 요구도 있지만, 실제 버그와 누락을 찾아 현재 작업에 집중하도록 돕기도 함

  - LLM의 검토 내용을 읽고 싶지 않다면 남은 문제가 경미할 때 에이전트가 직접 수정하게 하는 방법도 있음

## 최첨단 모델의 능력을 끝까지 활용할 필요는 없음

- 이 작업 방식은 의도적으로 최첨단 모델의 능력을 전부 사용하지 않음

- 최첨단 모델 기능에 의존하지 않을 이유에는 환경 비용과 책임이 있음

  - 에너지 사용량이 매우 크다는 우려가 있지만, 기업의 투명성이 낮아 어느 정도는 추정에 의존함

  - 자신보다 훨씬 영리한 것처럼 행동하는 도구를 신뢰하기는 어려우며, 결과 코드의 책임은 기계가 아니라 개발자에게 있음

  - 결과에 책임질 수 있으려면 사람이 과정의 필수적인 일부로 남아야 함

- 가장 고도화된 모델은 토큰 사용량이 커서 한 세션 안에 작업을 끝낼 수 있을지 불확실함

  - 더 작은 모델로 수행할 수 있는 작업이 더 안전한 선택임

  - 최첨단 모델이 필요 없는 작업 흐름이라면, 언젠가 공개 가중치 모델이나 오픈소스 모델로 대체해 공급자 의존에서 벗어날 여지도 있음

- 복잡한 개발 업무의 일부에서 사람과 같거나 조금 더 잘한다는 것만으로 개발자의 핵심 활동을 대체하기에는 부족함

  - 이를 대체하려면 사람보다 여러 배 뛰어나고, 자원을 덜 쓰며, 복잡한 현실에서 더 신뢰할 수 있어야 함

  - 인간 개발자 이상으로 의도에 부합하고, 결과에 대해서도 어떤 방식으로든 책임질 수 있어야 함

## 토큰 소진을 서비스 장애로 다루기

- 토큰이 떨어져 일이 멈추는 상황은 구매량 부족이라는 개인의 잘못보다 서비스 장애로 다루는 편이 적절함

  - 공급자가 세션 한도를 불투명하게 바꿀 수 있다면, 사용자는 구매한 자원을 계획적으로 쓰기 어려움

  - 이런 상황을 처리하는 유머로는 xkcd의 “컴파일 중”을 “토큰 없음”으로 바꿔 떠올릴 수 있음

- 토큰 절약은 필요하지만 충분한 대비책은 아님

  - 에이전트 구성, 사용 방식, 컨텍스트 크기, 스킬 설정 등을 재점검할 수 있음

  - 더 비싼 이용권을 사더라도 작업 중단을 완전히 피하지 못할 수 있음

- 기차나 비행기에서 인터넷 단절에 대비하듯, LLM도 접근할 수 없는 시간에 대비해야 함

  - 필요한 자료를 미리 내려받고 캐시하며, 오프라인에서도 할 일을 확보하는 것과 같은 원리임

- LLM에 맡기는 작업은 계속 활용할 수 있는 구체적인 산출물로 남겨야 함

  - 특히 사람이 코딩하는 방식에서는 언제든 직접 진행할 수 있는 계획된 작업 목록을 확보함

  - 에이전트를 쓸 수 없는 동안 그 목록을 구현하고, 접근이 복구되면 정리 작업을 맡길 수 있음

## 생성 텍스트 소비와 정신 건강 관리하기

- LLM 텍스트는 사람의 글과 다르며, 모델이 주제를 제대로 알지 못할 때 특히 질이 나빠짐

  - 이런 횡설수설하는 텍스트가 정신 건강에 해로울 가능성을 염두에 두고 과도하게 읽지 않는 편을 권함

  - 산출물은 자동 검토 에이전트가 거친 부분을 정리한 뒤 읽음

- 코드에 관해서는 계속 사람과 대화해야 함

  - 특히 큰 비전이나 흥미로운 측면은 사람끼리 이야기함

- 머리가 혼란스러우면 에이전트가 백그라운드에서 작업 중이지 않더라도 휴식을 취해야 함

  - 정신 건강이 작업 산출량보다 중요함

## PR과 커밋 메시지는 사람 사이의 소통임

- 프로그래밍은 대체로 사회적 활동이며, PR, 이슈, 커밋 메시지는 사람 사이의 소통 수단임

  - 혼자 개발하더라도 과거의 자신이 미래의 자신에게 기록을 남기는 셈임

- 다른 사람에게는 사람이 직접 작성한 소통을 먼저 제공해야 함

  - 완전히 생성된 PR을 그대로 보내지 않는 편을 권함

- 문법이 정확하고 모든 세부사항을 담았더라도 에이전트가 만든 PR 본문은 소통 자체가 아니라 도구 출력으로 취급함

  - 벤치마크 수치나 디버그 실행 추적처럼, 직접 쓴 PR 본문 뒤에 첨부함

  - 필요하면 `<details>` 안에 넣어 상대가 읽을지 선택하게 함

  - 멋진 작업이지만, 이제 PNG 속 코드도 LLM으로부터 안전하지 않음. 요즘 LLM은 이미지의 글자를 아주 잘 읽음.

- The Nemesis of Creativity를 읽다가 기계 사용을 거부하는 중국 현자의 구절을 봤는데, 이 글과 비슷하게 와닿음.

“기계를 쓰는 사람은 모든 일을 기계처럼 하게 되고, 기계처럼 일하면 마음도 기계처럼 변함. 기계의 마음을 품으면 소박함을 잃고, 소박함을 잃으면 마음의 지향도 흔들리게 됨. 그런 흔들림은 참된 분별과 맞지 않음. 이런 도구를 몰라서가 아니라, 쓰는 것을 부끄럽게 여기는 것임.”

- 솔직히 프로그래밍에 흥미를 잃었음. 벌 돈도 그리 많지 않고, 나는 노동시장이 요구하는 만큼 효율적이지 않으며, 함께 일하는 사람들은 껍데기만 남은 듯함. 모두가 그런 건 아니지만 그렇지 않은 사람들은 결국 회사를 떠남.

보람 있고 뜻이 맞는 사람들을 만날 수 있는 분야에 시간을 쓰고 싶음.

  - 예를 들면 어떤 분야이며, 그걸로 생계를 유지할 수 있는지 궁금함.

- 프로그래밍할 때 LLM을 쓰는 것 자체는 괜찮음. 적어도 내 방식으로는 경험과 지식, 취향을 활용해 단순히 바이브 코딩으로 맡길 때보다 나은 결과를 만든다고 느낌.

즐거움을 줄이는 것은 동료들의 LLM 사용 결과를 감당하는 일임. 인간 중계기와 대화하거나 엉뚱한 문제를 푸는 거대한 PR을 받는 건 즐겁지 않음. 절반쯤은 생각을 멈춘 것 같음. 더 빨리 만들지만, 필요한 것을 만들지는 못함.

  - 잘못된 결정을 커밋한 뒤 다음 PR에서 되돌리는 대신 우회하고, 그다음 PR에서는 최초의 잘못된 결정과 우회책을 또 우회하는 일이 반복됨.

결국 누적된 우회책과 예외 처리를 전부 머릿속에 넣고 변경 사항을 추론해야 해서 수동 검토가 불가능해짐.

  - [https://en.wikipedia.org/wiki/Third-person_effect](https://en.wikipedia.org/wiki/Third-person_effect)

  - 승진해서 아주 효율적이지만 세세한 관리가 필요한 팀을 맡은 느낌임. 경험 없는 사람들이 만든 결과도 봤지만, 나는 내 구상을 훨씬 빨리 구현할 수 있고 작은 기능 하나의 구현 시간에도 덜 얽매이게 됨.

다만 원래부터 프로그래밍 자체보다는 최종 결과물에 관심이 있었음.

  - LLM은 생각을 멈추고 싶은 사람을 위한 도구임. 팀이 나아지길 바란다면 먼저 사용을 중단하고 모범을 보여야 함. 생각을 멈추는 것이 용납되지 않는 환경을 만들어야 하며, 부하 직원들이 원하는 방식으로 LLM을 써 줄 거라고 기대할 수는 없음. 이 도구들은 바로 그들이 지금 사용하는 방식으로 쓰도록 설계되어 있음.
