# brownfield 하네스

## 문제

AI 개발 하네스는 대부분 **신규 프로젝트 전용**이다.
사내 3종(itnew-forge / itnew-plan+work / orbit)은 전부 기획 산출물(`docs/planning/`)이 없으면
**시작 자체가 막힌다** — 근거는 [02번 문서 §3](./02-inhouse-harness-audit.md) 참조.

그런데 실무의 절반은 이런 일이다:

> 남이 만들어 이미 배포한 서비스를 인수인계받았다.
> 인수인계 문서는 README 한 장.
> 클라이언트가 새 요구사항을 보내왔다.

여기에 하네스를 적용할 수 있는가?

---

## 1. 진단 — "하네스 = greenfield 전용"은 정확하지 않다

하네스의 본질은 **결정적 게이트 + 정본(source of truth) + 분업**이다.
사내 3종은 그중 **정본을 "사람이 미리 쓴 기획 문서"로 고정**했고, 그 선택이 greenfield 편향을 낳았다.

편향은 아키텍처의 본질이 아니라 **입력 계약의 선택**이다.
방증: orbit의 `orbit-tdd-driver` 는 컨텍스트로 *"기존 코드 파일 경로"* 를 이미 받는다.
즉 **실행부는 기존 코드베이스에서 동작하고, 막히는 것은 진입부뿐이다.**

**사내에도 역산 시도가 있었다.** itnew-dev 의 폐기된 `devlane` 스킬은
*"Controller.kt 존재 감지 → reverse 모드 → OpenAPI 역생성"* 을 갖고 있었다
(`itnew-dev/docs/LANE-MODEL.md:104` 이하, 현행 `skills/` 에는 없음).
다만 그것조차 전제가 *"`docs/planning/`, `task-breakdown.md` **존재**"* 였다 —
여기서 말한 "Brownfield"는 **하네스로 이미 시작한 프로젝트의 중간 재개**였지,
기획 문서 없는 남의 서비스가 아니었다. 자세한 경위는
[02번 문서 §3.2](./02-inhouse-harness-audit.md) 참조.

---

## 2. 발상의 전환

> brownfield 에서 정본은 **이미 돌아가고 있는 코드**다.
> 스펙을 새로 쓸 필요가 없다 — 이미 실행 가능한 형태로 존재한다.
> 문제는 그것이 **읽을 수 있는 형태가 아니라는 것**뿐이다.

따라서 과제는 "스펙 작성"이 아니라
**"코드에 잠긴 현재 동작을 실행 가능한 테스트로 꺼내기"** 가 된다.

이것이 Michael Feathers의 **characterization test** 다.
LLM과 궁합이 좋은 이유가 두 가지다:

1. **기계적 작업이라 LLM이 잘한다** — 실행 → 결과 캡처 → 고정
2. **없던 결정적 게이트가 생긴다** — characterization test는 정의상
   *"변경 전 코드에서 통과해야 하는"* 테스트이므로 `git stash` 로 진위를 **기계 판정**할 수 있다

두 번째가 핵심이다. greenfield 하네스의 "RED를 먼저 봤는가"에 대응하는,
**brownfield 고유의 결정적 검증**이 여기서 생긴다.

## 3. 핵심 원리 4가지

| # | brownfield 원리 | 뒤집는 greenfield 가정 |
|---|---|---|
| 1 | **정본은 코드다** — 문서를 만들지 말고 동작을 꺼내라 | 정본 = 사람이 쓴 PRD |
| 2 | **범위는 blast radius 다** — 전체 이해 시도 금지 | 전체 아키텍처를 먼저 설계 |
| 3 | **안전망 먼저** — characterization → 그 다음 TDD | RED 테스트 먼저 |
| 4 | **문서는 후불 적립** — 건드린 만큼만 | 문서를 선불로 전부 작성 |

**원리 2가 가장 중요하다.** brownfield에서 AI 작업이 실패하는 1번 원인은 **컨텍스트 폭발**이다.
"코드베이스를 이해한 뒤 고치겠다"는 접근은 토큰을 다 태우고, 읽은 것의 대부분을 쓰지 않는다.
읽을 범위를 **요청 하나에 걸린 실행 경로**로 강제 제한해야 한다.

**원리 4의 함의**: greenfield가 문서를 **선불**로 다 만들고 시작한다면,
brownfield는 **후불로, 건드린 만큼만 적립**한다.
N번 작업하면 N개 영역이 문서화된다 — **돌아다닌 만큼만 지도가 그려진다.**

## 4. 5-Stage 설계

| Stage | 빈도 | 목적 | 게이트 |
|---|---|---|---|
| **0 착륙** | 레포당 1회 | 테스트 러너를 초록으로 만든다 | **hard(기계)**: 테스트 명령 `exit 0` |
| **1 조준** | 요청당 1회 | 요청을 관측 가능한 동작 1개로 환원, blast radius 확정 | advisory: 20파일 초과 시 분할 경고 |
| **2 박제** | 요청당 1회 | 현재 동작을 characterization test로 고정 | **hard(기계)**: `git stash` 후 통과 |
| **3 변경** | TASK당 | 정상 TDD | **hard(사람)**: 깨진 박제가 회귀인가 의도인가<br>**hard(기계)**: test-presence, 전량 통과 |
| **4 적립** | 요청당 1회 | 알게 된 것만 문서에 추가 | — |

### Stage 0 — 착륙 (레포당 1회)

목표는 **게이트가 존재할 수 있는 상태**를 만드는 것이다. 이게 안 되면 나머지는 전부 무의미하다.

1. **실행 확인** — `docker compose up` 또는 README 절차로 서비스가 뜨는가
2. **테스트 러너 진단** (인수인계 레포는 실태가 제각각이므로 분기 필요):
   - 있고 초록 → 그대로 채택
   - 있는데 빨강 → **먼저 초록으로 만든다** (수정하거나 명시적 skip + 사유 기록)
   - 없음 → 최소 부트스트랩 (프레임워크 1개 + smoke test 1개만)
3. **산출** `docs/brownfield/LANDING.md` — 복붙 가능한 빌드·실행·테스트 명령 /
   디렉토리→책임 1장 요약 / 외부 의존과 로컬 대체 방법 / 위험 지대

> **게이트 0이 hard인 이유**: 빨간 상태에서 변경하면
> *"원래 빨간 건지 내가 깨뜨린 건지"* 구분이 불가능하다.
> 회귀 감지의 기준선이 없으면 이후 모든 게이트가 무의미해진다.

### Stage 1 — 조준 (요청당 1회)

클라이언트 요청을 **관측 가능한 동작 1개**로 환원한다.
진입점부터 실행 경로를 추적해 **blast radius** 를 확정한다.

산출에 반드시 포함할 것: **그 코드를 공유하는 다른 동작 목록** = 회귀 후보.
이것이 Stage 2에서 무엇을 추가로 박제할지 결정한다.

> **advisory**: blast radius가 20파일을 넘으면 요청을 쪼갠다.
> 여기서 안 쪼개면 Stage 2의 박제 비용이 폭발한다.

### Stage 2 — 박제 (요청당 1회) ← **핵심**

**outside-in 2단**으로 현재 동작을 고정한다:

- **2a. API 레벨** — 로컬 실행이 가능하면 여기부터. blast radius가 걸린 엔드포인트의
  현재 요청/응답을 캡처해 고정한다. **내부 구조를 몰라도 되고, 리팩터링에 안 깨진다.**
  인수인계 상황에서 비용 대비 효과가 가장 크다.
- **2b. 단위 레벨** — 실제로 수정할 함수·클래스에만 좁게.

> **절대 규칙: characterization test는 "옳은 동작"이 아니라 "현재 동작"을 기록한다.**
> **버그도 그대로 고정한다.** 고치고 싶은 게 보여도 여기서는 손대지 않는다.
> Stage 3에서 명시적으로 갱신하며, **그 diff 자체가 변경 기록이 된다.**

**게이트 2 (hard, 기계 판정):**

```bash
git stash push --include-untracked   # 내 변경을 되돌리고
<test command>                        # characterization test 만 실행
# → exit 0 이어야 한다.
#   실패하면 그것은 characterization 이 아니라 wishful test 다.
git stash pop                         # trap 으로 복원 보장
```

**`git stash pop` 실패는 데이터 손실이다.** 반드시 `trap ... EXIT` 로 잡고,
pop 실패 시 크게 경고해야 한다.

### Stage 3 — 변경 (TASK 단위)

이제 정상 TDD: 새 동작 실패 테스트(RED) → 구현(GREEN) → 정리(REFACTOR).

**게이트 3a (hard, 사람 판정)** — characterization test 전량 통과.
깨졌다면 두 갈래이고 **기계가 구분할 수 없다**:

| 갈래 | 처리 |
|---|---|
| 의도치 않은 회귀 | 구현을 고친다 |
| 의도한 동작 변경 | characterization을 갱신하고 그 diff를 변경 기록에 남긴다 |

**여기가 사람이 개입하는 유일한 필수 지점이자, TASK 경계 체크포인트다.**

**게이트 3b (hard, 기계)** — 기존 테스트 전량 통과
**게이트 3c (hard, 기계)** — test-presence: src 변경에 대응 테스트 동반 (Stop 훅, §6)

### Stage 4 — 적립 (요청당 1회)

이번에 **알게 된 것만** `LANDING.md` 에 덧붙인다 —
새로 이해한 모듈 1~2줄, 발견한 지뢰, 다음 사람이 알아야 할 것.

> **금지: 전체 문서화 시도.** 안 건드린 영역은 모른 채로 둔다.

## 5. 이 설계가 막는 실패 모드

| brownfield AI 작업 실패 모드 | 막는 장치 |
|---|---|
| **컨텍스트 폭발** — 코드베이스 전체를 읽으려 함 | Stage 1 blast radius + 분할 경고 |
| **환각적 이해** — 안 읽고 짐작으로 수정 | Stage 2 게이트 — 실제로 돌려서 통과해야 통과 |
| **조용한 회귀** — 관련 없어 보이는 곳이 깨짐 | 게이트 3a·3b + Stage 1의 공유 코드 영향 목록 |
| **테스트 없는 레포** | Stage 0 분기 (최소 부트스트랩) |
| **빨간 테스트 위에서 작업 시작** | 게이트 0 |
| **기획 문서가 없어 시작조차 못 함** | 정본을 코드로 재정의 — 문서 요구 자체를 제거 |

## 6. 구현 규모

**훅 1개 + 스킬 1개.**

| 산출물 | 역할 |
|---|---|
| `~/.claude/hooks/tdd-gate.mjs` | Stop 훅. src 변경에 테스트 미동반 시 턴 종료 차단 + 루프 가드 |
| `~/.claude/skills/brownfield/SKILL.md` | 5-Stage 절차 (`land`/`aim`/`pin`/`log` 서브커맨드) |
| `.../scripts/verify-characterization.sh` | 게이트 2 (`git stash` → test → exit code, `trap` 복원 보장) |
| `.../templates/` | `LANDING.md`, `change.md` |
| `<project>/.claude/tdd-gate.json` | **프로젝트별 opt-in.** 없으면 훅은 조용히 통과 |

### Stop 훅 로직

```
1. stdin JSON 파싱 → cwd 획득
2. <cwd>/.claude/tdd-gate.json 없거나 enabled:false → exit 0 (조용히 통과)
3. git 저장소 아니면 → exit 0
4. git status --porcelain 으로 미커밋 변경 파일 수집
5. 분류: ignorePatterns 제외 → testPatterns 매치 = 테스트 → 코드 확장자 = src
6. src 변경 있음 && 테스트 변경 없음 → 차단 후보
7. 루프 가드: 변경 집합 해시를 상태 파일과 대조
   - 같은 해시로 이미 차단했으면 → exit 0 + 경고 1줄
   - 처음 보는 해시면 → 기록 후 exit 2
8. exit 2 stderr: 변경된 src 목록 + 다음 행동 지시
```

**루프 가드는 선택이 아니다.** Claude Code 공식 문서에 Stop 훅 무한 루프 방지 장치가 없다 —
설계 근거는 [01번 문서 §3.3](./01-prose-vs-deterministic-gates.md) 참조.

### 왜 전역 훅 + 프로젝트별 opt-in 인가

인수인계 레포를 여러 개 오가므로 프로젝트마다 훅을 재설치하는 건 비현실적이다.
반대로 문서 전용 레포에서 시끄러우면 안 된다.
→ **훅은 전역에 두고, `tdd-gate.json` 이 있는 프로젝트에서만 활성화한다.**

### 규모 대조

| | itnew-forge | 이 설계 |
|---|---|---|
| 에이전트 | 26개 | 0개 |
| 문서량 | 2,988줄 | 스킬 1개 |
| TDD 강제 | 산문 (메인 LLM이 자기 판정) | 훅 (기계 판정) |

차이는 기능이 아니라 **집행자가 LLM인가 기계인가**이다.

## 7. 사례 시뮬레이션

**상황**: 지자체 축제 포털. A가 구현·배포 후 이탈, B가 인수인계.
인수인계 문서는 README 한 장. 스택 Next.js + Spring Boot, `docker-compose.yml` 있음.

**클라이언트 신규 요청**
① 축제 신청 시 신청자에게 SMS 확인 문자 발송
② 마감일이 지났는데 신청이 됨 — 차단해달라

### Act 0 — 착륙 (첫날 오전, 1회성)

`./gradlew test` → **14개 중 3개 실패**. 게이트 0이 걸리고 작업이 시작되지 않는다.

| 실패 테스트 | 정체 | 처리 |
|---|---|---|
| `마감일_이후_신청_거부됨` | **A가 테스트만 쓰고 구현 안 함** — 요구사항 ②의 정답이 이미 존재 | `@Disabled` + 사유 기록 |
| `공지_정렬` | 하드코딩 날짜 의존, 시간 경과로 깨짐 | 상대 날짜로 수정 |
| `SmsClient.발송_성공` | 실제 외부 게이트웨이 호출 | `@Tag("external")` 로 분리 |

→ 13/13 통과. 게이트 0 통과. `LANDING.md` 산출.

> **관찰**: 게이트 0이 없었다면 빨간 테스트는 배경 소음이 됐을 것이고,
> **A가 남긴 정답 테스트(요구사항 ②)를 발견하지 못했을 것이다.**

### Act 1 — 조준 (첫날 오후)

```
POST /api/festivals/{id}/applications
  └ FestivalApplicationController.apply()
      └ FestivalApplyService.apply()        ← 변경 지점
          ├ FestivalRepository.findById()
          ├ ApplicationRepository.save()
          └ (SMS 발송 없음)                  ← 추가할 곳

blast radius: 4 파일
⚠️ 코드 공유로 영향받을 다른 동작:
   - GET /api/admin/applications  (ApplicationRepository 공유)
   - 축제 상세 조회                (FestivalRepository 공유)
   → 회귀 후보. Act 2에서 같이 박제.
```

**읽은 파일 4개 + 확인차 2개.** 레포가 300파일이어도 무관하다.

### Act 2 — 박제 (둘째 날 오전)

docker compose로 띄워 API 레벨로 현재 응답을 캡처한다.
마감 지난 축제가 `201`로 통과하는 **명백한 버그를 그대로 고정한다**:

```kotlin
@Test
fun `현재 동작 - 마감일 지난 축제도 신청이 접수된다`() {
    // ⚠️ characterization: 올바른 동작이 아니라 '현재' 동작.
    //    요구사항 ②에서 의도적으로 변경 예정.
    assertEquals(201, post("/api/festivals/2/applications", 유효한_신청서).status)
}
```

**여기서 LLM이 실제로 자주 내는 사고**: "마감이면 당연히 400이지"라고 판단해
`assertEquals(400, ...)` 을 쓴다. 게이트 2가 이를 잡는다:

```
git stash → ./gradlew test --tests '*Characterization*'
✗ expected: 400 but was: 201
⛔ characterization 이 아니라 wishful test 입니다.
   변경 전 코드에서 통과하지 않는 테스트는 안전망이 될 수 없습니다.
git stash pop
```

**exit code가 판정하므로 사람이 고민할 필요가 없다.** 최종 박제 6건(회귀 후보 2건 포함).

### Act 3 — 변경 (둘째 날 오후~)

LLM이 구현부터 손대자 **Stop 훅이 턴 종료를 차단**:

```
⛔ 변경된 src 에 대응 테스트가 없습니다: FestivalApplyService.kt
   실패하는 테스트를 먼저 작성하거나, 의도적 예외라면 사용자 확인을 받으세요.
```

→ `@Disabled` 테스트를 되살려 RED 확인 후 구현. 다시 Stop → 통과.

이어서 **박제가 깨진다** (`201` → `400`). **게이트 3a — 사람이 판정한다.**
B가 "의도한 변경" 선택 → 테스트 갱신, **그 diff가 변경 기록이 된다.**

나머지 5건 통과 = **관리자 목록 조회가 안 깨졌음이 확인됨.** 이것이 안전망의 값어치다.

요구사항 ①(SMS)은 외부 의존이라 **seam**(인터페이스 추출)을 낸다.
`LANDING.md` 의 *"위험 지대: api/sms/ 테스트 없음"* 이 여기서 설계 판단의 근거가 된다 —
**첫날의 기록이 이틀 뒤에 값을 한다.**

> **관찰**: 잘하고 있으면 Stop 훅은 조용하다. **훅은 존재를 드러내지 않을 때가 정상이다.**

### Act 4 — 적립 (셋째 날)

알게 된 것만 `LANDING.md` 에 덧붙인다. `web/`, `api/notice/` 는 **여전히 문서에 없다.**
안 건드렸기 때문이다.

### 결과

A가 남긴 건 README 한 장이었지만, 셋째 날 B는 **테스트 19개짜리 안전망**을 갖고 있다.
인수인계 문서를 더 요구해서 얻은 것이 아니라 **돌아가는 코드에서 꺼낸 것**이다.

## 8. 일반화 가능한 교훈

특정 도구와 무관하게 전이되는 것들:

1. **legacy 코드는 스펙이 없는 게 아니라, 읽을 수 없는 형태로 있는 것이다.**
   문서화가 아니라 **추출(extraction)** 이 답이다.
2. **범위 제한이 brownfield AI 작업의 1번 성공 요인이다.**
   "전체를 이해한 뒤 고친다"는 접근은 거의 항상 실패한다.
3. **문서는 후불 적립이 지속 가능하다.** 선불 전량 문서화는 인수인계에서 거의 항상 실패한다.
4. **버그를 그대로 박제하는 규율이 안전망의 전제다.**
   "이건 명백히 잘못됐으니 고쳐서 기록하자"는 유혹이 안전망을 wishful test로 만든다.
5. **기계 판정과 사람 판정의 경계를 명시적으로 설계하라.**
   "박제가 깨졌다"는 기계가 알지만 "회귀인가 의도인가"는 사람만 안다.
   이 경계가 곧 체크포인트의 위치다.
6. **하네스의 적용 범위는 정본 선택이 결정한다.**
   정본을 사람이 쓰는 산출물로 잡으면 greenfield 전용이 되고,
   코드로 잡으면 brownfield에서도 작동한다.

## 9. 한계 및 미검증 사항

- **본 설계는 2026-08-10 기준 미구현·미검증이다.** 실사용 데이터가 없다.
- **게이트 3c는 "테스트가 같이 변경됐는가"까지만 본다.**
  RED를 실제로 봤는지는 증명하지 못한다.
  이는 itnew-forge의 test-presence 게이트(`phases/lane.md:166-170`)와 **판정 로직이 동일**하며,
  차이는 **집행 위치**뿐이다 — forge는 team-lead LLM이 실행 여부를 결정하지만,
  훅은 재량 없이 항상 발화한다.
  테스트 실행 결과를 PostToolUse로 적립해 RED 증거까지 잡는 것은 v2 후보이며 미설계.
- **Stage 2의 API 레벨 characterization은 로컬 실행 가능한 서비스를 전제한다.**
  운영 환경에만 존재하는 시스템에서는 단위 레벨로 낮춰야 하고, 그만큼 안전망이 얇아진다.
- **characterization test는 만능이 아니다.** 비결정적 동작(시각, 난수, 외부 API),
  대량 상태 의존, 비동기 타이밍에 의존하는 코드는 박제가 어렵다.
  이런 영역은 seam을 먼저 내야 하는데, seam을 내는 것 자체가 변경이라 닭-달걀 문제가 생긴다.
  (Feathers의 원저가 이 문제에 상당 분량을 할애한다 — 필요 시 원저 참조)
- **Stage 0에서 "테스트가 아예 없는 레포"의 부트스트랩 비용을 과소평가했을 수 있다.**
  프레임워크 선정·CI 연동·픽스처 설계가 실제로는 며칠 걸릴 수 있다.
- 시뮬레이션(§7)은 **실제 프로젝트 기록이 아니라 설계 검토용 가상 사례**다.
